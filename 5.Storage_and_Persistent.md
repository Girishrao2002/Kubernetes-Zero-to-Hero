# Kubernetes Storage and Persistent Storage

Kubernetes is designed to run applications in containers, but containers are generally treated as **ephemeral**. A container can be restarted, recreated, or replaced at any time. If application data is stored only inside the container's writable filesystem, that data may be lost when the container is removed.

Kubernetes Storage provides mechanisms for:

- Temporary storage
- Sharing data between containers in a Pod
- Persistent application data
- Configuration
- Secrets and credentials
- Stateful applications such as databases

This README provides a detailed explanation of Kubernetes Storage, including:

1. Kubernetes Volumes
2. `emptyDir`
3. `local` volumes
4. PersistentVolumes (PV)
5. PersistentVolumeClaims (PVC)
6. StorageClasses
7. Dynamic provisioning
8. Access modes

# 1. Why Does Kubernetes Need Storage?

A container has its own writable filesystem.

```text
Pod
└── Container
    └── Container Filesystem
        ├── /app
        ├── /tmp
        ├── /var
        └── /data
```

Suppose an application writes:

```text
/data/users.db
```

If the container is deleted and recreated, the new container normally gets a new writable filesystem.

```text
Old Container
└── /data/users.db
        |
        X
    Container deleted

New Container
└── /data/
    └── users.db does not exist
```

This is acceptable for stateless applications, but it is a problem for applications such as:

- MySQL
- PostgreSQL
- MongoDB
- Elasticsearch
- Kafka
- Applications that store uploaded files
- Applications that generate persistent reports

Kubernetes therefore provides storage abstractions that separate application data from the container's writable layer.

A useful way to understand Kubernetes storage is to think in layers:

```text
Application

    v

PV

    v
```

Not every volume uses every layer.

For example:

```text
emptyDir

```

Whereas persistent storage commonly looks like:

```text
Pod

      |

           |
           └── Storage Backend
```

# 3. What Is a Kubernetes Volume?

A Kubernetes **Volume** is a directory accessible by one or more containers in a Pod.

A volume is defined in the Pod specification:

```yaml
spec:
  volumes:
    - name: app-data
      emptyDir: {}
```

It is then mounted into a container:

```yaml
containers:
  - name: app
    image: nginx

    volumeMounts:
      - name: app-data
        mountPath: /data
```

The relationship is:

```text
volumes
   |
   | defines
   v
app-data
   |
   | mounted through
   v
volumeMounts
   |
   v
/data inside container
```

The name must match:

```yaml
volumes:
  - name: app-data
```

and:

```yaml
volumeMounts:
  - name: app-data
```

---

# 4. `volumes` vs `volumeMounts`

This distinction is extremely important.

## `volumes`

Defines the storage source.

```yaml
volumes:
  - name: data
    emptyDir: {}
```

Think:

> What storage do I want?

## `volumeMounts`

Defines where the storage appears inside the container.

```yaml
volumeMounts:
  - name: data
    mountPath: /data
```

Think:

> Where should the storage be mounted?

Together:

```text
Volume definition
       |
       v
     data
       |
       v
volumeMount
       |
       v
/data
```

# 5. `emptyDir`

`emptyDir` is one of the simplest Kubernetes volume types.

Example:

```yaml
volumes:
  - name: data
    emptyDir: {}
```

When a Pod is created, Kubernetes creates an initially empty directory for that volume.

```text
Pod
 |
 +-- Container A
 |
 +-- Container B
 |
 └── emptyDir
       |
       └── /data
```

Containers in the same Pod can mount the same `emptyDir`.

---

# 6. `emptyDir` Example

```yaml
apiVersion: v1
kind: Pod

metadata:
  name: emptydir-demo

spec:
  containers:

    - name: writer
      image: busybox

      command:
        - sh
        - -c
        - |
          while true; do
            date >> /data/log.txt
            sleep 5
          done

      volumeMounts:
        - name: shared-data
          mountPath: /data

    - name: reader
      image: busybox

      command:
        - sh
        - -c
        - |
          while true; do
            cat /data/log.txt
            sleep 5
          done

      volumeMounts:
        - name: shared-data
          mountPath: /data

  volumes:
    - name: shared-data
      emptyDir: {}
```

Architecture:

```text
                  Pod
                   |
          +--------+--------+
          |                 |
       Writer             Reader
          |                 |
          +--------+--------+
                   |
               emptyDir
                   |
              /data/log.txt
```

The writer creates:

```text
/data/log.txt
```

The reader can read the same file.

---

# 7. `emptyDir` Lifecycle

The most important rule:

> `emptyDir` survives container restarts but is deleted when the Pod is removed.

Consider:

```text
Pod
 |
 +-- Container A
 +-- Container B
 |
 └── emptyDir
```

If Container A crashes:

```text
Container A  -> restarted
Container B  -> still running
emptyDir     -> remains
```

If the entire Pod is deleted:

```text
Pod -> deleted
     |
     └── emptyDir -> deleted
```

Therefore `emptyDir` should not normally be used as the primary storage for important persistent application data.

---

# 8. `emptyDir` with Memory

`emptyDir` can use memory instead of disk.

```yaml
volumes:
  - name: cache
    emptyDir:
      medium: Memory
```

You can also specify a size limit:

```yaml
volumes:
  - name: cache
    emptyDir:
      medium: Memory
      sizeLimit: 256Mi
```

This is useful for:

- Temporary caches
- Scratch space
- High-speed temporary files
- Sharing temporary data between containers

Because memory is used, the application must be designed with appropriate resource limits and expectations.

---

# 9. When Should You Use `emptyDir`?

Good use cases include:

### Temporary processing

```text
Download
   |
   v
emptyDir
   |
   v
Process
   |
   v
Delete
```

### Shared data between containers

```text
Container A
    |
    v
emptyDir
    |
    v
Container B
```

### Temporary cache

```text
Application
    |
    v
emptyDir
    |
    v
Cache
```

Avoid using `emptyDir` for important data that must survive Pod deletion.

# 10. Local Volumes

A `local` volume represents storage physically associated with a particular Kubernetes node.

For example:

```text
Worker Node 1
└── /mnt/data
```

A local PersistentVolume can reference that path.

Example:

```yaml
apiVersion: v1
kind: PersistentVolume

metadata:
  name: local-pv

spec:
  capacity:
    storage: 10Gi

  accessModes:
    - ReadWriteOnce

  persistentVolumeReclaimPolicy: Retain

  local:
    path: /mnt/data

  nodeAffinity:
    required:
      nodeSelectorTerms:
        - matchExpressions:
            - key: kubernetes.io/hostname
              operator: In
              values:
                - worker-node-1
```

---

# 11. Why Does a Local PV Need Node Affinity?

Local storage belongs to a particular node.

For example:

```text
Node 1
└── /mnt/data
```

If a Pod using that storage is scheduled onto Node 2:

```text
Node 2
└── /mnt/data
```

that is not the same storage.

Therefore Kubernetes needs to know that the PV is tied to Node 1.

Node affinity tells the scheduler:

> This PV can only be used on nodes matching this condition.

Architecture:

```text
             Kubernetes Cluster

       +-------------------------+
       |        Node 1           |
       |                         |
       |   /mnt/data             |
       |       |                 |
       |       v                 |
       |    Local PV             |
       +-------------------------+
```

---

# 12. Advantages and Disadvantages of Local Storage

## Advantages

- Very low latency
- High performance
- Uses local disk
- Useful for workloads that benefit from local storage

## Disadvantages

- Tied to a node
- Node failure can make the data unavailable
- Requires careful scheduling
- Does not automatically provide distributed replication

Local storage is therefore different from distributed storage systems such as cloud block storage or network/distributed filesystems.

# 13. Persistent Storage

For important application data, Kubernetes provides:

- PersistentVolume
- PersistentVolumeClaim
- StorageClass

These are usually discussed together.

```text
PV  = Storage provided

PVC = Storage requested

StorageClass = Storage provisioning mechanism
```

# 14. PersistentVolume (PV)

A **PersistentVolume (PV)** is a storage resource available to the Kubernetes cluster.

A PV is a cluster-level resource.

Example:

```yaml
apiVersion: v1
kind: PersistentVolume

metadata:
  name: my-pv

spec:
  capacity:
    storage: 10Gi

  accessModes:
    - ReadWriteOnce

  persistentVolumeReclaimPolicy: Retain

  hostPath:
    path: /mnt/data
```

A PV describes storage characteristics such as:

- Capacity
- Access modes
- Reclaim policy
- Storage backend
- Volume mode
- Node affinity where applicable

---

# 15. PersistentVolumeClaim (PVC)

A **PersistentVolumeClaim (PVC)** is a request for storage.

Instead of a developer directly selecting a physical disk, the application requests storage through a PVC.

Example:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim

metadata:
  name: my-pvc

spec:
  accessModes:
    - ReadWriteOnce

  resources:
    requests:
      storage: 5Gi
```

Think:

```text
PV
|
| "I provide storage."
|
PVC
|
| "I need storage."
```

---

```text
Administrator
      |
      v
PersistentVolume

      v
Storage

      |
PersistentVolumeClaim
      ^
      |
```

A more complete model:

```text
                         Kubernetes Cluster
                                |
                 +--------------+--------------+
                 |                             |
                PV                            PVC
                 |                             |
                 +-------------+---------------+
                               |
                              Pod
                               |
                            /data
```

# 19. PV vs PVC

| Feature | PersistentVolume | PersistentVolumeClaim |
|---|---|---|
| Meaning | Storage resource | Request for storage |
| Usually created by | Administrator/provisioner | Application/developer |
| Scope | Cluster resource | Namespace-scoped |
| Represents | Actual available storage | Requested storage |
| Example | 100Gi disk | Request for 10Gi |
| Used by Pod directly? | No | Yes |

The Pod normally references the PVC, not the PV.

# 20. PV Access Modes

Kubernetes supports several access mode concepts.

## ReadWriteOnce (RWO)

The volume may be mounted read-write by a single node.

```text
Node 1
 |
 +-- Pod A
 |
 +-- Pod B
 |
 +-- Volume
```

The exact behavior across Pods depends on the storage backend.

---

## ReadOnlyMany (ROX)

The volume can be mounted read-only by multiple nodes where supported.

```text
Node 1 ---+
Node 2 ---+---> Volume
Node 3 ---+
```

---

## ReadWriteMany (RWX)

The volume can be mounted read-write by multiple nodes where supported.

```text
Node 1 ---+
Node 2 ---+---> Shared Volume
Node 3 ---+
```

Common examples of storage systems that can support shared filesystem-style access include NFS and cloud/network filesystems.

---

# 21. Important: Access Modes Depend on the Storage Backend

Not every storage backend supports every access mode.

For example, a typical cloud block volume may support `ReadWriteOnce`, while a shared network filesystem may support `ReadWriteMany`.

Therefore:

> Do not choose an access mode independently of the storage backend.

Always verify what the underlying CSI driver or storage implementation supports.

---

# 22. Reclaim Policies

A PersistentVolume can have a reclaim policy.

Common policies include:

- `Retain`
- `Delete`

## Retain

```yaml
persistentVolumeReclaimPolicy: Retain
```

When the PVC is deleted, the PV/data can be retained for manual recovery or cleanup.

Conceptually:

```text
PVC deleted
    |
    v
PV remains
    |
    v
Data can be preserved
```

This is useful when data protection is important.

---

## Delete

```yaml
persistentVolumeReclaimPolicy: Delete
```

When the PVC is deleted, the dynamically provisioned storage may also be deleted, depending on the provisioner and backend.

This is useful when storage should follow the lifecycle of the claim.

Always understand the storage backend's behavior before using `Delete` for important data.

---

# 23. StorageClass

Manually creating PVs does not scale well.

Imagine hundreds of applications requesting storage.

Instead of manually creating a PV for every application, Kubernetes can use a **StorageClass**.

A StorageClass describes a class of storage and how it should be dynamically provisioned.

Conceptually:

```text
PVC
 |
 v
StorageClass
 |
 v
Provisioner / CSI Driver
 |
 v
Storage Backend
 |
 v
PV
```

---

# 24. Static vs Dynamic Provisioning

## Static Provisioning

Administrator creates the PV first.

```text
Administrator
     |
     v
PV
     |
     v
PVC
     |
     v
Pod
```

## Dynamic Provisioning

Application creates a PVC.

```text
Application
     |
     v
PVC
     |
     v
StorageClass
     |
     v
Provisioner
     |
     v
Storage
     |
     v
PV
```

Dynamic provisioning is the normal approach in many modern Kubernetes environments.

---

# 25. Generic StorageClass Example

A StorageClass commonly looks conceptually like:

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass

metadata:
  name: fast-storage

provisioner: example.com/driver

parameters:
  type: fast

reclaimPolicy: Delete

volumeBindingMode: WaitForFirstConsumer
```

The exact `provisioner` and `parameters` depend on your Kubernetes environment and CSI driver.

Do not copy the example provisioner into a real cluster unless that driver actually exists.

---

# 26. PVC Using a StorageClass

```yaml
apiVersion: v1
kind: PersistentVolumeClaim

metadata:
  name: database-storage

spec:
  storageClassName: fast-storage

  accessModes:
    - ReadWriteOnce

  resources:
    requests:
      storage: 20Gi
```

Flow:

```text
PVC
 |
 | storageClassName: fast-storage
 v
StorageClass
 |
 v
CSI Provisioner
 |
 v
Storage Backend
 |
 v
PV
```

---

# 27. Dynamic Provisioning

Dynamic provisioning means Kubernetes can automatically create storage when a PVC requests it.

For example:

```yaml
resources:
  requests:
    storage: 20Gi
```

The workflow becomes:

```text
1. Developer creates PVC
          |
          v
2. Kubernetes finds StorageClass
          |
          v
3. CSI provisioner creates storage
          |
          v
4. Kubernetes creates/binds PV
          |
          v
5. Pod mounts PVC
```

This removes much of the manual storage administration.

# 28. ConfigMap as a Volume

A ConfigMap stores non-sensitive configuration.

Example:

```yaml
apiVersion: v1
kind: ConfigMap

metadata:
  name: app-config

data:
  application.properties: |
    server.port=8080
    environment=production
```

It can be mounted as a volume.

```yaml
volumes:
  - name: config
    configMap:
      name: app-config
```

Mount it:

```yaml
volumeMounts:
  - name: config
    mountPath: /etc/config
```

Inside the container:

```text
/etc/config/
└── application.properties
```

---

# 29. Why Use ConfigMaps?

Without ConfigMaps:

```text
Application Image
 |
 +-- application code
 +-- configuration
```

With ConfigMaps:

```text
Application Image
 |
 └── Application code

ConfigMap
 |
 └── Environment-specific configuration
```

The same container image can therefore be deployed into different environments.

```text
              Same Image
                  |
       +----------+----------+
       |          |          |
      DEV        TEST       PROD
       |          |          |
    ConfigMap  ConfigMap  ConfigMap
```

# 30. Secret as a Volume

Secrets are intended for sensitive configuration such as:

- Passwords
- API tokens
- TLS certificates
- SSH keys
- Other credentials

Example:

```yaml
apiVersion: v1
kind: Secret

metadata:
  name: db-secret

type: Opaque

stringData:
  username: admin
  password: mypassword
```

Mount it:

```yaml
volumes:
  - name: secret-volume
    secret:
      secretName: db-secret
```

Then:

```yaml
volumeMounts:
  - name: secret-volume
    mountPath: /etc/secrets
```

Inside the container:

```text
/etc/secrets/
├── username
└── password
```

---

# 31. ConfigMap vs Secret

| Feature | ConfigMap | Secret |
|---|---|---|
| Configuration | Yes | Yes |
| Passwords | No | Yes |
| API keys | No | Yes |
| Certificates | Usually no | Yes |
| Volume mounting | Yes | Yes |
| Environment variables | Yes | Yes |
| Intended for sensitive data | No | Yes |

Important security note:

> Kubernetes Secret values are commonly represented using base64 encoding in manifests/API objects. Base64 is not encryption. Encryption at rest depends on cluster configuration.

Use appropriate RBAC, encryption-at-rest configuration, access controls, and external secret-management solutions where required.

# 32. StatefulSets

A **StatefulSet** is a Kubernetes workload resource designed for applications that require stable identity and/or persistent storage.

Typical examples include:

- Databases
- Distributed databases
- Kafka
- ZooKeeper
- Some clustered applications
- Stateful services requiring stable network identities

---

# 33. Deployment vs StatefulSet

A Deployment normally treats Pods as interchangeable.

```text
Deployment
   |
   +-- Pod A
   +-- Pod B
   +-- Pod C
```

If Pod A is deleted:

```text
Pod A -> deleted
```

Kubernetes creates another Pod, potentially with a different name.

A StatefulSet provides stable identity.

```text
StatefulSet
   |
   +-- app-0
   +-- app-1
   +-- app-2
```

If `app-1` is recreated:

```text
app-1 -> deleted
   |
   v
app-1 -> recreated
```

The ordinal identity remains.

---

# 34. StatefulSet Key Features

A StatefulSet provides mechanisms for:

### 1. Stable Pod identity

```text
app-0
app-1
app-2
```

### 2. Stable network identity

Pods can be addressed predictably, especially when combined with a headless Service.

### 3. Stable storage

Each Pod can have its own PVC.

### 4. Ordered operations

StatefulSets can manage Pod creation and termination in an ordered manner, subject to the StatefulSet configuration.

---

# 35. StatefulSet Pod Naming

Suppose:

```yaml
replicas: 3
```

StatefulSet:

```text
mysql
```

Pods can be:

```text
mysql-0
mysql-1
mysql-2
```

These ordinal identities are important for many stateful systems.

# 36. StatefulSet and Persistent Storage

This is one of the most important Kubernetes storage patterns.

Suppose:

```text
StatefulSet
replicas: 3
```

Kubernetes can create:

```text
mysql-0
mysql-1
mysql-2
```

Each can have separate persistent storage:

```text
mysql-0 -> PVC -> PV -> Storage
mysql-1 -> PVC -> PV -> Storage
mysql-2 -> PVC -> PV -> Storage
```

Architecture:

```text
                 StatefulSet
                      |
        +-------------+-------------+
        |             |             |
      mysql-0       mysql-1       mysql-2
        |             |             |
       PVC-0         PVC-1         PVC-2
        |             |             |
       PV-0          PV-1          PV-2
        |             |             |
     Storage-0     Storage-1     Storage-2
```

---

# 37. `volumeClaimTemplates`

StatefulSets use `volumeClaimTemplates` to automatically create a PVC for each StatefulSet Pod.

Example:

```yaml
volumeClaimTemplates:

  - metadata:
      name: data

    spec:
      accessModes:
        - ReadWriteOnce

      resources:
        requests:
          storage: 10Gi
```

For three replicas, Kubernetes can create a separate claim for each Pod.

Conceptually:

```text
StatefulSet
   |
   +-- mysql-0
   |     |
   |     +-- data-mysql-0
   |
   +-- mysql-1
   |     |
   |     +-- data-mysql-1
   |
   +-- mysql-2
         |
         +-- data-mysql-2
```

The exact PVC names are generated from the claim template and StatefulSet/Pod identity.

---

# 38. Complete StatefulSet Example

```yaml
apiVersion: apps/v1
kind: StatefulSet

metadata:
  name: web

spec:

  serviceName: web

  replicas: 3

  selector:
    matchLabels:
      app: web

  template:

    metadata:
      labels:
        app: web

    spec:

      containers:

        - name: nginx
          image: nginx

          volumeMounts:
            - name: data
              mountPath: /usr/share/nginx/html

  volumeClaimTemplates:

    - metadata:
        name: data

      spec:

        accessModes:
          - ReadWriteOnce

        resources:
          requests:
            storage: 1Gi
```

Architecture:

```text
StatefulSet: web
      |
      +---- web-0 ---- data PVC
      |
      +---- web-1 ---- data PVC
      |
      +---- web-2 ---- data PVC
```

---

# 39. Headless Service

StatefulSets are commonly used with a headless Service.

Example:

```yaml
apiVersion: v1
kind: Service

metadata:
  name: web

spec:
  clusterIP: None

  selector:
    app: web

  ports:
    - port: 80
```

The important field is:

```yaml
clusterIP: None
```

This creates a headless Service.

It allows DNS-based discovery of individual StatefulSet Pods.

Conceptually:

```text
web-0.web
web-1.web
web-2.web
```

The complete DNS name also includes the Kubernetes namespace and cluster DNS suffix.

---

# 40. StatefulSet Architecture

A typical architecture is:

```text
                    Client / Application
                            |
                            v
                    Headless Service
                            |
             +--------------+--------------+
             |              |              |
             v              v              v
          web-0          web-1          web-2
             |              |              |
             v              v              v
           PVC-0          PVC-1          PVC-2
             |              |              |
             v              v              v
            PV-0           PV-1           PV-2
             |              |              |
          Storage-0       Storage-1       Storage-2
```

This gives each instance:

- Stable identity
- Stable storage association
- Predictable network identity

---

# 41. What Happens When a StatefulSet Pod Dies?

Suppose:

```text
mysql-1
```

fails.

Kubernetes can recreate:

```text
mysql-1
```

rather than creating a random replacement identity.

Its persistent claim can remain associated with that ordinal identity.

Conceptually:

```text
Before:

mysql-1
   |
   +-- data-mysql-1


Pod fails


After:

mysql-1
   |
   +-- data-mysql-1
```

This allows the replacement Pod to reconnect to its persistent storage, subject to the storage backend, scheduling constraints, and normal Kubernetes storage behavior.

---

# 42. StatefulSet Does Not Automatically Make an Application Distributed

This is a very important distinction.

Creating:

```text
StatefulSet
replicas: 3
```

does not automatically make a database highly available.

For example:

```text
mysql-0
mysql-1
mysql-2
```

does not automatically mean MySQL replication has been configured.

The application itself must support and be configured for:

- Replication
- Leader election
- Clustering
- Failover
- Data consistency

Kubernetes provides identity, scheduling, lifecycle, and storage mechanisms. The application is still responsible for its own distributed-system behavior.

| Feature | Deployment | StatefulSet |
|---|---|---|
| Pod identity | Interchangeable | Stable |
| Pod names | Generated | Predictable ordinal names |
| Stable network identity | Not the primary purpose | Yes |
| Per-Pod storage | Possible but not the primary pattern | Strongly supported |
| `volumeClaimTemplates` | No | Yes |
| Typical use | Stateless applications | Stateful applications |
| Examples | Web server, API | Database, clustered service |

# 48. Common Storage Mistakes

## Mistake 1: Using `emptyDir` for database data

```text
Database
   |
emptyDir
```

If the Pod is deleted, the data is lost.

Use persistent storage for important database data.

---

## Mistake 2: Confusing PV and PVC

Remember:

```text
PV = storage resource

PVC = request for storage
```

---

## Mistake 3: Assuming every storage backend supports RWX

Access modes depend on the storage backend.

---

## Mistake 4: Treating Secret base64 as encryption

Base64 is an encoding mechanism.

It does not by itself provide confidentiality.

---

## Mistake 5: Assuming StatefulSet creates database replication

StatefulSet provides Kubernetes-level identity and lifecycle mechanisms.

The database still needs its own replication/cluster configuration.

---

## Mistake 6: Ignoring the storage backend

A PVC is an abstraction.

The actual behavior depends heavily on:

```text
CSI driver
     |
Storage backend
```

# 49. Important Concepts Beyond the Basics

After learning PV, PVC, and StorageClass, the next storage topics to study are:

## CSI

**Container Storage Interface**

CSI provides a standard interface for storage systems to integrate with Kubernetes.

Architecture:

```text
Kubernetes
    |
    v
CSI Driver
    |
    v
Storage System
```

Examples include cloud disks, cloud filesystems, NFS-based systems, and distributed storage platforms.

---

## Volume Expansion

Some storage systems support increasing a PVC's requested capacity.

For example:

```text
10Gi
 |
 v
20Gi
```

This depends on the StorageClass/CSI driver and filesystem support.

---

## Volume Snapshots

Snapshots provide point-in-time copies of persistent volumes when supported by the environment.

Conceptually:

```text
PV
 |
 +---- Snapshot
```

Snapshots can be useful for:

- Backup workflows
- Test environments
- Data recovery
- Cloning workflows

A snapshot is not automatically a complete backup strategy.

---

## Backup and Restore

Production storage requires thinking beyond Kubernetes objects.

Consider:

```text
Application
    |
Persistent Data
    |
Backup
    |
Off-cluster / durable backup storage
    |
Restore procedure
```

A database backup should generally be designed with application consistency in mind.

# 51. Quick Revision

### Volume

Provides storage to containers in a Pod.

### emptyDir

Temporary Pod-scoped storage.

```text
Container restart -> data remains
Pod deletion       -> data removed
```

### local

Storage physically associated with a specific node.

### PersistentVolume

Cluster storage resource.

```text
PV = Storage provided
```

### PersistentVolumeClaim

Request for storage.

```text
PVC = Storage requested
```

### StorageClass

Defines/provides a mechanism for dynamically provisioning storage.

### ConfigMap

Non-sensitive configuration.

### Secret

Sensitive configuration such as credentials and certificates.

### StatefulSet

Workload controller for applications requiring stable identity and persistent storage patterns.

### volumeClaimTemplates

Creates a PVC template so StatefulSet Pods can receive their own persistent claims.

### Headless Service

Provides DNS-based discovery for individual StatefulSet Pods.

```text

          app-0              app-1              app-2

             v                  v                  v

                                |

                                |
```
