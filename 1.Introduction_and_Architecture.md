# Kubernetes — Introduction & Architecture

## 1. Introduction to Kubernetes

### What is Kubernetes?

Kubernetes (often abbreviated as **K8s**) is an open-source platform for **automating the deployment, scaling, and management of containerized applications**.

A simple way to think about it is:

```text
Containers
    ↓
Many containers
    ↓
Multiple machines
    ↓
Kubernetes
    ↓
Automated management
```

Kubernetes provides a common platform for running applications reliably across a cluster of machines.

---

## Why Do We Need Kubernetes?

Running a small number of containers manually is straightforward.

For example:

```bash
docker run nginx
docker run backend
docker run frontend
```

But as an application grows, several operational problems appear.

### 1. Container failures

A container can crash unexpectedly.

```text
Application
    ↓
Container
    ↓
   CRASH
```

Someone or something needs to detect the failure and restore the application.

### 2. Scaling

Suppose one backend container is no longer sufficient:

```text
Before:

Backend
  ↓
1 container
```

You may need:

```text
After:

Backend
  ↓
┌───────┬───────┬───────┐
│       │       │       │
Pod     Pod     Pod
```

Kubernetes can maintain the required number of application instances.

### 3. Machine failures

Applications may run across multiple machines.

If one machine fails:

```text
Node 1  →  FAILED
Node 2  →  Running
Node 3  →  Running
```

Kubernetes can help maintain workloads on the remaining available infrastructure, depending on the workload and cluster configuration.

### 4. Application updates

Updating applications manually can cause downtime or inconsistent versions.

Kubernetes provides mechanisms such as **rolling updates** and **rollbacks**.

### 5. Networking

With many containers running across multiple machines, applications need reliable ways to communicate with one another.

Kubernetes provides abstractions for:

- Service discovery
- Load balancing
- Internal networking
- External access

### 6. Desired state management

Instead of manually telling Kubernetes every action to perform, you describe the state you want.

For example:

```text
I want 5 instances of my backend application.
```

Kubernetes continuously works toward that state.

---

# Kubernetes and Docker

Docker and Kubernetes solve different problems.

### Docker

Docker focuses primarily on building, packaging, and running containers.

```text
Application
    ↓
Docker Image
    ↓
Container
    ↓
Run
```

### Kubernetes

Kubernetes focuses on orchestrating containerized workloads across a cluster.

```text
Containerized Applications
            ↓
       Kubernetes
            ↓
 ┌──────────┼──────────┐
 ↓          ↓          ↓
Deploy     Scale      Manage
 ↓          ↓          ↓
Network    Heal       Update
```

Kubernetes does not mean "Docker at a larger scale." It is an orchestration and management platform that can work with supported container runtimes.

---

# Kubernetes Cluster

A Kubernetes environment is called a **cluster**.

A cluster consists of:

- A **Control Plane**, which manages the cluster
- One or more **Worker Nodes**, which run application workloads

```text
                 Kubernetes Cluster
                         │
          ┌──────────────┴──────────────┐
          │                             │
     Control Plane                  Worker Nodes
                                      │
                         ┌────────────┼────────────┐
                         │            │            │
                       Node 1       Node 2       Node 3
```

---

# 2. Architecture of Kubernetes

Kubernetes follows a distributed architecture with two major areas:

```text
                Kubernetes Cluster
                         │
        ┌────────────────┴────────────────┐
        │                                 │
   CONTROL PLANE                     WORKER NODES
        │                                 │
        │                         ┌───────┼───────┐
        │                         │       │       │
        │                      kubelet kube-proxy Runtime
        │
   ┌────┼──────────────┐
   │    │              │
   ↓    ↓              ↓
 API   Scheduler   Controller
Server              Manager
   │
   ↓
  etcd
```

The **Control Plane** manages the desired state and makes cluster-level decisions.

The **Worker Nodes** provide the compute environment where application Pods run.

---

# Control Plane Components

The Control Plane consists primarily of:

1. kube-apiserver
2. etcd
3. kube-scheduler
4. kube-controller-manager
5. cloud-controller-manager, when used

---

## 2.1 kube-apiserver

The **kube-apiserver** is the central API endpoint of Kubernetes.

It is the main communication interface between users, cluster components, and the Kubernetes API.

For example:

```bash
kubectl get pods
```

Conceptually:

```text
User
  ↓
kubectl
  ↓
Kubernetes API
  ↓
kube-apiserver
```

The API server:

- Exposes the Kubernetes API
- Receives API requests
- Authenticates requests
- Authorizes requests
- Performs admission processing
- Validates API objects
- Coordinates persistence of cluster state
- Provides API access to Kubernetes components

A useful mental model:

> **The API server is the front door of the Kubernetes cluster.**

---

## 2.2 etcd

**etcd** is a distributed key-value store used to persist Kubernetes cluster state.

Kubernetes needs to store information such as:

- Cluster configuration
- Nodes
- Pods
- Deployments
- Services
- Desired state
- Other Kubernetes object data

Conceptually:

```text
             kube-apiserver
                    │
                    ↓
                   etcd
                    │
          ┌─────────┼─────────┐
          ↓         ↓         ↓
        Pods     Services  Deployments
```

Important distinction:

> The API server is the interface to Kubernetes; etcd is the persistent backing store for Kubernetes cluster state.

etcd is not normally the application database for your workloads. For example, an application may still use PostgreSQL, MySQL, MongoDB, or another database for its own data.

---

## 2.3 kube-scheduler

The **kube-scheduler** selects an appropriate worker node for Pods that do not yet have a node assignment.

Suppose a cluster has three worker nodes:

```text
Node 1
Node 2
Node 3
```

A new Pod is created:

```text
Pod
 │
 └── Node = not assigned
```

The scheduler evaluates the available nodes and scheduling constraints.

```text
                  Pod
                   │
                   ↓
              Scheduler
                   │
        ┌──────────┼──────────┐
        ↓          ↓          ↓
      Node 1     Node 2     Node 3
                   ↑
                Selected
```

Scheduling decisions can consider factors such as:

- Available CPU and memory
- Node affinity
- Pod affinity and anti-affinity
- Taints and tolerations
- Topology constraints
- Other scheduling requirements

Important:

> **The scheduler selects a node; it does not run the container itself.**

---

## 2.4 kube-controller-manager

Kubernetes uses **controllers** to continuously compare the desired state with the observed state.

For example:

```text
Desired replicas = 3
Actual replicas  = 2
```

A controller detects the difference and takes action to move the cluster toward:

```text
Desired replicas = 3
Actual replicas  = 3
```

The conceptual control loop is:

```text
Desired State
     ↓
Observe Current State
     ↓
Compare
     ↓
Take Corrective Action
     ↓
Observe Again
     ↺
```

The `kube-controller-manager` runs a collection of Kubernetes controllers.

This controller-based architecture is one of the fundamental ideas behind Kubernetes.

---

## 2.5 cloud-controller-manager

The **cloud-controller-manager** contains cloud-provider-specific control logic when Kubernetes is integrated with a cloud provider.

It can manage or coordinate functionality such as:

- Cloud load balancers
- Cloud networking/routes
- Node integration
- Other cloud-specific resources

It is not required in every Kubernetes environment.

---

# Worker Node Components

A Worker Node contains the components required to run application workloads.

The major Kubernetes-related components are:

1. kubelet
2. Container Runtime
3. kube-proxy

---

## 2.6 kubelet

The **kubelet** is the primary Kubernetes agent running on a node.

Its job is to ensure that the Pods assigned to its node are running and healthy according to their specifications.

Conceptually:

```text
Control Plane
     ↓
Pod specification
     ↓
   kubelet
     ↓
Container Runtime
     ↓
  Containers
```

The kubelet:

- Runs on each node
- Manages Pods assigned to the node
- Communicates with the container runtime
- Starts and stops containers as required
- Performs health-related checks
- Reports node and Pod status through the Kubernetes API

A useful mental model:

> **The kubelet is the agent that manages Kubernetes workloads on a node.**

---

## 2.7 Container Runtime

The **container runtime** is responsible for running containers.

Examples include:

- containerd
- CRI-O

Conceptually:

```text
Kubernetes
    ↓
 kubelet
    ↓
Container Runtime
    ↓
Container
```

Kubernetes communicates with the container runtime through the **Container Runtime Interface (CRI)**.

This is why Kubernetes should not be thought of as simply "Docker."

Docker is a container platform, while Kubernetes is an orchestration platform.

---

## 2.8 kube-proxy

`kube-proxy` is a node-level component associated with implementing Kubernetes **Service networking**.

A simplified view is:

```text
             Client
                │
                ↓
             Service
                │
       ┌────────┼────────┐
       ↓        ↓        ↓
     Pod 1    Pod 2    Pod 3
```

The exact networking implementation can vary depending on the Kubernetes networking solution and cluster configuration.

For the foundation level, remember:

> **Services provide stable networking abstractions for workloads, and kube-proxy is a traditional node-level component involved in implementing Service networking.**

Detailed Kubernetes networking will be covered separately.

# How the Components Work Together

Consider this simple request:

```bash
kubectl apply -f pod.yaml
```

The high-level flow is:

```text
                     kubectl
                        │
                        ↓
                 kube-apiserver
                        │
             ┌──────────┼──────────┐
             ↓          ↓          ↓
           etcd     Scheduler   Controllers
                        │
                        ↓
                  Selected Node
                        │
                        ↓
                     kubelet
                        │
                        ↓
                Container Runtime
                        │
                        ↓
                    Container
```

Let's understand this flow step by step.

### Step 1 — User submits configuration

The user sends a request through `kubectl`.

```text
kubectl
   ↓
API Server
```

### Step 2 — API Server processes the request

The API server handles mechanisms such as:

```text
Authentication
      ↓
Authorization
      ↓
Admission
      ↓
Validation
```

### Step 3 — State is persisted

The relevant Kubernetes state is persisted through the API server in etcd.

```text
API Server
    ↓
  etcd
```

### Step 4 — Scheduler selects a node

If the Pod has no node assignment, the scheduler selects a suitable worker node.

```text
Pod
 ↓
Scheduler
 ↓
Node 2
```

### Step 5 — kubelet manages the Pod

The kubelet on the selected node works to make the Pod run.

```text
Node 2
  ↓
kubelet
```

### Step 6 — Container runtime starts the container

```text
kubelet
   ↓
Container Runtime
   ↓
Container
```

### Step 7 — Status is reported

The node reports the observed state back through the Kubernetes API.

Eventually:

```text
Pod
 ↓
Running
```

# Desired State and Reconciliation

This is the most important architectural concept in Kubernetes.

Suppose you declare:

```text
replicas: 3
```

You are expressing:

```text
Desired State = 3 replicas
```

Kubernetes observes the actual cluster:

```text
Actual State = 2 replicas
```

A controller works to reconcile the difference.

```text
        Desired State
              │
              ↓
         Kubernetes
              │
              ↓
        Actual State
              │
              ↓
       Compare States
              │
              ↓
       Take Corrective
           Action
              │
              ↓
        Observe Again
```

The goal is continuously:

```text
Desired State ≈ Actual State
```
