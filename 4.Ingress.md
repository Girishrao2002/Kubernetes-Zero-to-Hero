# 1. Introduction

Kubernetes provides several networking abstractions for exposing applications. A **Pod** has an IP address, and a **Service** provides a stable endpoint for a group of Pods.

Modern applications often need more than a stable Service endpoint:

- Multiple applications behind one public entry point
- Host-based routing
- Path-based routing
- HTTPS/TLS termination
- Certificate management
- HTTP request routing
- Centralized external access
- Routing to multiple Services

This is where **Ingress** fits into the Kubernetes networking model.

```text
                    INTERNET
                       |
                       v
                External Entry Point
                       |
                       v
              Ingress Controller
                       |
                Ingress Rules
                       |
          +------------+------------+
          |            |            |
          v            v            v
      frontend      backend      payments
       Service       Service       Service
          |            |            |
          v            v            v
         Pods         Pods         Pods
```

> **Ingress provides HTTP/HTTPS routing rules for traffic entering a Kubernetes cluster and normally routes that traffic to Services.**

---

# 2. Why Ingress Is Needed

Suppose a cluster contains:

```text
frontend
backend
payments
orders
users
admin
```

Without an HTTP routing layer, each application could be exposed independently:

```text
Internet
   |
   +---- LoadBalancer → frontend-service
   |
   +---- LoadBalancer → backend-service
   |
   +---- LoadBalancer → payments-service
```

This can result in multiple external entry points and more infrastructure/configuration.

Ingress can provide a shared HTTP/HTTPS entry point:

```text
                         Internet
                            |
                            v
                  Ingress Controller
                            |
          +-----------------+-----------------+
          |                 |                 |
          v                 v                 v
     /frontend            /api             /payments
          |                 |                 |
          v                 v                 v
    frontend-svc      backend-svc      payment-svc
```

A single external HTTP/HTTPS entry point can route requests to different Services.

---

# 3. What Is Kubernetes Ingress?

Ingress is a Kubernetes API resource that defines rules for routing **HTTP and HTTPS traffic** to Services.

An Ingress rule can use:

- Hostname
- URL path
- TLS configuration
- Backend Service

Conceptually:

```text
example.com/
        |
        v
frontend-service

example.com/api
        |
        v
backend-service

example.com/payments
        |
        v
payment-service
```

Ingress itself is **not the network proxy**.

```text
Ingress
    =
routing configuration

Ingress Controller
    =
software that implements the routing
```

Creating an Ingress object without a suitable controller does not automatically make external HTTP traffic work.

# 4. Ingress vs Service

## Service

A Service provides a stable network abstraction for a set of Pods.

```text
Service
   |
   +---- Pod
   +---- Pod
   +---- Pod
```

It provides:

- Stable virtual IP
- Stable DNS name
- Service-level traffic distribution
- A way to discover Pods without using their individual IP addresses

## Ingress

Ingress provides HTTP/HTTPS routing to Services.

```text
Ingress
   |
   +---- frontend-service
   |
   +---- backend-service
   |
   +---- payment-service
```

The normal relationship is:

```text
Ingress
   |
   v
Service
   |
   v
Pods
```

| Capability | Service | Ingress |
|---|---|---|
| Stable endpoint for Pods | Yes | Not its primary purpose |
| Service discovery | Yes | Uses Services |
| Selects Pods | Yes | Normally routes to Services |
| HTTP path routing | No | Yes |
| Host-based HTTP routing | No | Yes |
| TLS termination | Not its primary role | Commonly supported by controllers |
| External HTTP entry point | Possible with certain Service types | Yes, when implemented by a controller |
| Primary role | Service networking | HTTP/HTTPS routing |

Mental model:

```text
Ingress = Which application should receive this HTTP request?

Service = Which Pods currently provide that application?
```

# 5. Ingress Architecture

A simplified architecture:

```text
                         CLIENT
                            |
                            | HTTP/HTTPS
                            v
                     External Entry Point
                            |
                            v
                 +-----------------------+
                 | Ingress Controller    |
                 |                       |
                 | HTTP/HTTPS proxy      |
                 | Routing engine        |
                 +-----------+-----------+
                             |
                       Ingress rules
                             |
              +--------------+--------------+
              |              |              |
              v              v              v
        frontend-svc   backend-svc   payment-svc
              |              |              |
              v              v              v
            Pods           Pods           Pods
```

There are two major conceptual planes.

## Control/configuration plane

The controller watches resources such as:

- Ingress
- IngressClass
- Services
- EndpointSlices
- Secrets
- Controller-specific resources

It uses that information to construct or update routing configuration.

## Data plane

The proxy/load-balancing component processes network traffic.

```text
Kubernetes API
       |
       v
Ingress Controller
       |
       v
Proxy configuration
       |
       v
HTTP/HTTPS traffic
```

> The controller watches Kubernetes state and configures the data plane; the data plane processes application traffic.

# 6. Ingress Controller

An **Ingress Controller** is software that watches Kubernetes resources and implements Ingress rules.

Kubernetes defines the Ingress API, but does not itself provide one universal proxy implementation.

```text
                 Kubernetes API Server
                         |
                         v
                Ingress Controller
                         |
              +----------+----------+
              |                     |
              v                     v
       Watch resources        Configure proxy
                                    |
                                    v
                               Data plane
                                    |
                                    v
                                 Services
```

Possible controller implementations include:

- NGINX-based controllers
- Traefik-based controllers
- HAProxy-based controllers
- Cloud-provider integrations
- Other networking platforms

> **Ingress is an API abstraction; the Ingress Controller supplies the implementation.**

# 8. IngressClass

`IngressClass` identifies the controller responsible for handling an Ingress resource.

```text
Ingress
   |
   | ingressClassName
   v
IngressClass
   |
   v
Ingress Controller
```

An Ingress can specify:

```yaml
spec:
  ingressClassName: nginx
```

This is especially important when a cluster has multiple controllers:

```text
Cluster
 |
 +-- nginx-controller
 |
 +-- internal-controller
 |
 +-- cloud-controller
```

Different Ingress resources can be associated with different classes.

Ingress routing rules generally combine:

```text
Host
  +
Path
  +

```

For example:

```text

Path: /api
Backend: backend-service
```

A request:

```text
GET https://example.com/api/users
```

can be evaluated by:

```text
Host match:
example.com

+

Path match:
/api

↓

backend-service
```

# 10. Host-Based Routing

Host-based routing routes requests according to the hostname.

```text
www.example.com
        |
        v
frontend-service

api.example.com
        |
        v
backend-service

admin.example.com
        |
        v
admin-service
```

This is also called **virtual hosting**.

Multiple logical applications can share the same external infrastructure.

---

# 11. Path-Based Routing

Path-based routing uses the URL path.

```text
example.com/
        |
        v
frontend-service

example.com/api
        |
        v
backend-service

example.com/payments
        |
        v
payment-service
```

For example:

```text
https://example.com/
https://example.com/api
https://example.com/payments
```

can reach different Services.

---

# 12. Path Types

Kubernetes Ingress defines three path types:

```text
Exact
Prefix
ImplementationSpecific
```

## Exact

An `Exact` path matches an exact URL path.

```text
path: /api
pathType: Exact
```

This is intended to match `/api`, rather than treating it as a prefix for `/api/users`.

## Prefix

A `Prefix` path matches based on a URL path prefix.

```text
path: /api
pathType: Prefix
```

It can match paths such as:

```text
/api
/api/users
/api/products
/api/orders/123
```

## ImplementationSpecific

With:

```text
pathType: ImplementationSpecific
```

the interpretation depends on the Ingress Controller.

For portable configurations, `Exact` and `Prefix` are the most important path types to understand.

# 13. Default Backend

An Ingress can define a default backend.

Conceptually:

```text
                  Ingress
                     |
          +----------+----------+
          |                     |
       Rule match          No rule match
          |                     |
          v                     v
      Specific Service      Default Backend
```

The default backend can provide a response for traffic that does not match an explicit routing rule, subject to controller behavior and configuration.

Common uses include:

- Generic 404 pages
- Default application responses
- Handling unknown hosts or paths

# 14. Service Backends

Ingress normally sends traffic to a Service rather than directly to individual Pods.

```text
Ingress
   |
   v
frontend-service
   |
   +---- Pod A
   +---- Pod B
   +---- Pod C
```

This creates a useful abstraction:

```text
Pods are ephemeral
        ↓
Service provides stable access
        ↓
Ingress provides HTTP routing
```

Therefore:

```text
Ingress
   ↓
Service
   ↓
Pods
```

# 15. Service, EndpointSlice, and Pod Relationship

Suppose:

```text
frontend-service
```

selects:

```text
app=frontend
```

and three matching Pods exist:

```text
Pod A → 10.244.1.10
Pod B → 10.244.1.11
Pod C → 10.244.2.10
```

Kubernetes maintains endpoint information through EndpointSlices.

```text
                 Service
                    |
                    v
               EndpointSlice
              /      |                   v       v       v
          Pod A    Pod B    Pod C
```

If Pod B disappears:

```text
Before:

Service
   |
EndpointSlice
   +-- Pod A
   +-- Pod B
   +-- Pod C


After:

Service
   |
EndpointSlice
   +-- Pod A
   +-- Pod C
   +-- Pod D
```

The set of available endpoints changes dynamically.

An Ingress Controller can observe these changes and update its routing behavior.

# 18. TLS Termination

TLS termination occurs when the Ingress Controller terminates the external TLS connection.

```text
Client
  |
  | HTTPS
  v
Ingress Controller
  |
  | decrypted HTTP
  v
Service
  |
  v
Pod
```

The controller handles the external TLS session.

Benefits can include:

- Centralized certificate management
- Centralized HTTPS configuration
- Reduced TLS configuration inside individual applications
- Easier certificate handling for multiple hosts

An alternative architecture can keep encryption between the ingress layer and backend as well:

```text
Client
  |
  | HTTPS
  v
Ingress
  |
  | HTTPS
  v
Service
  |
  v
Pod
```

The exact behavior depends on the controller and configuration.

# 19. TLS Secrets

Kubernetes can store TLS certificate material in a Secret commonly using:

```text
kubernetes.io/tls
```

Conceptually:

```text
TLS Secret
 |
 +-- tls.crt
 |
 +-- tls.key
```

An Ingress can associate a hostname with a TLS Secret.

```text
Ingress
 |
 +-- Host: example.com
 |
 +-- TLS Secret: example-tls
```

The Ingress Controller can use the certificate for HTTPS traffic.

Important distinction:

> A Kubernetes TLS Secret stores certificate material. Certificate issuance and renewal are separate concerns.

# 20. Ingress Annotations

Many Ingress Controllers support controller-specific annotations.

NGINX-based implementations have historically provided annotations for features such as:

- HTTP-to-HTTPS redirects
- URL rewrite behavior
- Authentication
- Rate limiting
- Proxy settings
- Request-size limits
- Timeouts

Conceptually:

```yaml
metadata:
  annotations:
    controller-specific-key: "value"
```

Annotations are controller-specific.

A configuration supported by one controller may not be supported by another.

Therefore, controller documentation is essential when using annotations.

# 26. Ingress vs NodePort

NodePort exposes a Service through a port on Kubernetes nodes:

```text
Client
  |
  v
NodeIP:NodePort
  |
  v
Service
  |
  v
Pods
```

Ingress provides application-aware HTTP routing:

```text
Client
  |
  v
Ingress Controller
  |
  +---- Host/path
  |
  v
Service
  |
  v
Pods
```

NodePort can be useful for simple exposure and as part of certain load-balancing architectures.

Ingress is more expressive for HTTP/HTTPS application routing.

# 27. Ingress vs Gateway API

Gateway API is the newer Kubernetes networking API model designed to support richer traffic-management use cases.

Ingress:

```text
Ingress
   |
   +-- HTTP/HTTPS routing
```

Gateway API:

```text
Gateway
   |
   +-- HTTPRoute
   +-- TLSRoute
   +-- TCPRoute
   +-- UDPRoute
```

Gateway API also provides stronger separation between infrastructure configuration and application routing.

For example:

```text
Platform team
     |
     v
Gateway

Application team
     |
     v
HTTPRoute
```

Important current perspective:

> Ingress remains a stable Kubernetes API, while Gateway API is the recommended direction for new feature development.

# 29. Security Considerations

Ingress is often a public application entry point, so security matters.

## TLS

Prefer HTTPS for applications carrying sensitive information.

```text
Internet
   |
 HTTPS
   ↓
Ingress
```

## Certificate management

Certificates require:

- Issuance
- Storage
- Renewal
- Rotation
- Monitoring

Tools such as cert-manager can automate certificate lifecycle management.

## Authentication

Depending on the controller and architecture, authentication can be implemented at the ingress layer or through external identity systems.

## Authorization

Authentication asks:

> Who are you?

Authorization asks:

> What are you allowed to do?

Ingress should not be assumed to replace application-level authorization.

## Rate limiting

Some controllers support rate limiting:

```text
Client
   |
   v
Ingress
   |
   | Rate limit
   v
Application
```

## NetworkPolicy

Ingress routing and network authorization are separate concepts.

Ingress determines HTTP routing.

NetworkPolicy controls allowed network communication at the Pod/network layer when supported by the cluster's networking implementation.

# 30. Ingress Troubleshooting Theory

When an Ingress application doesn't work, follow the traffic path.

A useful chain is:

```text
DNS
 ↓
External IP / Load Balancer
 ↓
Ingress Controller
 ↓
IngressClass
 ↓
Ingress rule
 ↓
TLS
 ↓
Service
 ↓
EndpointSlice
 ↓
Pod
 ↓
Application
```

Each layer can fail independently.

## 30.1 DNS problem

```text
example.com
   ↓
doesn't resolve
```

The request may never reach Kubernetes.

## 30.2 External entry point problem

DNS resolves correctly, but the external address isn't reachable.

Possible causes:

- Load balancer configuration
- Firewall rules
- Security groups
- Network routing
- NodePort configuration
- Cloud networking

## 30.3 Controller problem

The Ingress resource exists, but no controller is processing it.

Questions:

- Is an Ingress Controller installed?
- Is it running?
- Is the correct IngressClass selected?

## 30.4 Ingress rule problem

The controller is running but the request doesn't match:

- Host
- Path
- PathType

## 30.5 TLS problem

Possible causes:

- Missing TLS Secret
- Incorrect certificate
- Incorrect hostname
- Expired certificate
- Incorrect Secret type
- Controller-specific TLS configuration issue

## 30.6 Service problem

Ingress may successfully route to a Service, but the Service itself may be wrong:

- Wrong Service name
- Wrong Service port
- Wrong target port
- Wrong selector

## 30.7 Endpoint problem

A Service may exist but have no usable endpoints:

```text
Ingress
   ↓
Service
   ↓
EndpointSlice
   ↓
No matching Pods
```

A common cause is a selector mismatch.

## 30.8 Pod problem

The endpoint exists but the Pod isn't healthy.

Potential causes:

- CrashLoopBackOff
- Readiness failure
- Application not listening
- Wrong container port
- Application error

# 33. Interview Questions and Answers

## Q1. What is Kubernetes Ingress?

Ingress is a Kubernetes API resource that defines HTTP/HTTPS routing rules for traffic entering a cluster and routes that traffic to Services.

## Q2. Is Ingress a Service?

No.

```text
Ingress → HTTP/HTTPS routing
Service → stable access to Pods
```

## Q3. Does Kubernetes Ingress automatically work after creating an Ingress object?

No. A suitable Ingress Controller must be installed and configured to implement the Ingress resource.

## Q4. What is an Ingress Controller?

Software that watches Kubernetes resources and implements the routing rules defined by Ingress resources.

## Q5. What is host-based routing?

Routing requests based on the hostname.

```text
api.example.com → backend-service
www.example.com → frontend-service
```

## Q6. What is path-based routing?

Routing requests based on the URL path.

```text
example.com/     → frontend-service
example.com/api  → backend-service
```

## Q7. What is the difference between Exact and Prefix?

`Exact` matches an exact path. `Prefix` matches paths beginning with the specified prefix.

## Q8. What is IngressClass?

IngressClass identifies the controller that should handle an Ingress resource.

## Q9. Can Ingress route directly to Pods?

The standard Ingress model normally routes to a Service backend rather than directly targeting individual Pods.

## Q10. What is TLS termination?

TLS termination occurs when the Ingress Controller terminates the external HTTPS connection and decrypts the traffic before forwarding it to the backend.

## Q11. Where are TLS certificates commonly stored?

In Kubernetes Secrets, commonly using:

```text
kubernetes.io/tls
```

## Q12. What is cert-manager?

cert-manager is a Kubernetes add-on that automates certificate issuance and lifecycle management.

## Q13. What is the difference between Ingress and LoadBalancer Service?

A LoadBalancer Service exposes a particular Service externally. Ingress provides HTTP/HTTPS routing that can direct traffic to multiple Services.

## Q14. What happens when a backend Pod dies?

Kubernetes updates endpoint information for the Service. The Service can route traffic to available endpoints, and an Ingress Controller can observe those changes.
