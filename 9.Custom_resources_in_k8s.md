# Kubernetes Custom Resources --- Detailed --------------------------

# 1. Introduction

Kubernetes provides many built-in resources:

-   Pod
-   Deployment
-   ReplicaSet
-   Service
-   ConfigMap
-   Secret
-   StatefulSet
-   DaemonSet
-   Job
-   CronJob
-   Ingress

These resources cover a large part of container orchestration.

However, Kubernetes is also designed to be **extensible**.

Suppose an organization wants Kubernetes to understand concepts such as:

-   Database
-   PostgreSQLCluster
-   RedisCluster
-   Backup
-   Certificate
-   Application
-   VirtualMachine
-   CloudDatabase
-   MessageQueue

These are not standard Kubernetes resources.

Kubernetes allows us to create our own API resources using **Custom
Resource Definitions (CRDs)**.

The overall relationship is:

``` text
CustomResourceDefinition (CRD)
            |
            | defines
            v
      Custom Resource (CR)
            |
            | watched by
            v
       Controller
            |
            | reconciles
            v
    Actual Kubernetes Resources
```

The key idea is:

> A CRD defines a new Kubernetes resource type, a Custom Resource is an
> instance of that type, and a controller/operator can act on that
> resource.

------------------------------------------------------------------------

# 2. What Is a Kubernetes Resource?

A Kubernetes resource is an object managed through the Kubernetes API.

For example:

``` yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx
spec:
  replicas: 3
```

This describes a Deployment object.

Important fields include:

  Field          Purpose
  -------------- --------------------------------------------
  `apiVersion`   API group and version
  `kind`         Resource type
  `metadata`     Name, namespace, labels, annotations, etc.
  `spec`         Desired state
  `status`       Current observed state

Example:

``` yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx
spec:
  containers:
    - name: nginx
      image: nginx:latest
```

Kubernetes already knows what a `Pod` is and how to process it.

------------------------------------------------------------------------

# 3. Why Custom Resources?

Imagine you operate databases on Kubernetes.

Without Custom Resources, users might need to create many Kubernetes
objects manually:

``` text
StatefulSet
Service
ConfigMap
Secret
PersistentVolumeClaim
PodDisruptionBudget
Backup configuration
Monitoring configuration
```

Instead, you could expose a higher-level API:

``` yaml
apiVersion: database.example.com/v1
kind: Database
metadata:
  name: production-db
spec:
  engine: postgres
  version: "16"
  replicas: 3
```

The user only describes the desired database.

A controller can then create and manage all the underlying Kubernetes
resources.

This gives Kubernetes a domain-specific API.

------------------------------------------------------------------------

# 4. What Is a Custom Resource?

A **Custom Resource (CR)** is an instance of a custom API resource added
to Kubernetes.

For example:

``` yaml
apiVersion: database.example.com/v1
kind: Database

metadata:
  name: production-db

spec:
  engine: postgres
  version: "16"
  replicas: 3
```

Here:

-   `Database` is the custom kind.
-   `database.example.com` is the API group.
-   `v1` is the API version.
-   `production-db` is the resource name.
-   `spec` contains the desired configuration.

After the CRD is installed, Kubernetes can store this object in its API.

------------------------------------------------------------------------

# 5. CRD, CR, Controller, and Operator

These terms are related but different.

## 5.1 Custom Resource Definition --- CRD

A CRD defines a new resource type.

Think:

> "Teach Kubernetes about a new kind of object."

Example:

``` text
Database
```

------------------------------------------------------------------------

## 5.2 Custom Resource --- CR

A CR is an actual object created from that definition.

Example:

``` text
Database: production-db
```

------------------------------------------------------------------------

## 5.3 Controller

A controller watches resources and tries to make actual state match
desired state.

For example:

``` text
Desired:
3 database replicas

Actual:
2 database replicas
```

The controller takes action to reach:

``` text
Actual:
3 database replicas
```

This process is called **reconciliation**.

------------------------------------------------------------------------

## 5.4 Operator

An Operator is a Kubernetes controller pattern that contains
application/domain-specific operational knowledge.

For example, a PostgreSQL Operator may know how to:

-   Deploy PostgreSQL
-   Configure PostgreSQL
-   Create users
-   Perform backups
-   Handle failover
-   Scale replicas
-   Upgrade PostgreSQL
-   Recover from failures

A simplified model is:

``` text
CRD
 +
Controller
 +
Domain-specific operational knowledge
 =
Operator
```

------------------------------------------------------------------------

# 6. Custom Resource Definition (CRD)

A CRD is itself a Kubernetes resource.

Example:

``` yaml
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: databases.database.example.com

spec:
  group: database.example.com

  names:
    kind: Database
    plural: databases
    singular: database

  scope: Namespaced

  versions:
    - name: v1
      served: true
      storage: true

      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              type: object
              properties:
                engine:
                  type: string

                version:
                  type: string

                replicas:
                  type: integer
```

The CRD tells the Kubernetes API server:

> There is a new resource type called `Database`.

------------------------------------------------------------------------

# 7. Anatomy of a CRD

Let's break the CRD down.

## 7.1 `apiVersion`

``` yaml
apiVersion: apiextensions.k8s.io/v1
```

This identifies the Kubernetes API used to create the CRD.

------------------------------------------------------------------------

## 7.2 `kind`

``` yaml
kind: CustomResourceDefinition
```

This tells Kubernetes that the object being created is a CRD.

------------------------------------------------------------------------

## 7.3 `metadata.name`

``` yaml
metadata:
  name: databases.database.example.com
```

The CRD name follows this general convention:

``` text
<plural>.<group>
```

For example:

``` text
databases.database.example.com
```

where:

``` text
plural = databases
group  = database.example.com
```

------------------------------------------------------------------------

## 7.4 `spec.group`

``` yaml
group: database.example.com
```

The API group identifies the custom API.

A common naming pattern is:

``` text
<domain>/<resource>
```

For example:

``` text
database.example.com
```

------------------------------------------------------------------------

## 7.5 `spec.names`

``` yaml
names:
  kind: Database
  plural: databases
  singular: database
```

### Kind

``` yaml
kind: Database
```

Used in the resource manifest:

``` yaml
kind: Database
```

### Plural

``` yaml
plural: databases
```

Used with commands such as:

``` bash
kubectl get databases
```

### Singular

``` yaml
singular: database
```

Useful as the singular resource name.

------------------------------------------------------------------------

## 7.6 Scope

``` yaml
scope: Namespaced
```

A CRD can define either:

``` yaml
scope: Namespaced
```

or:

``` yaml
scope: Cluster
```

More details are covered later.

------------------------------------------------------------------------

## 7.7 Versions

Example:

``` yaml
versions:
  - name: v1
    served: true
    storage: true
```

This defines the API version.

A custom API may evolve through versions such as:

``` text
v1alpha1
v1beta1
v1
```

------------------------------------------------------------------------

## 7.8 Schema

The schema defines the structure and types of the resource.

Example:

``` yaml
schema:
  openAPIV3Schema:
    type: object
    properties:
      spec:
        type: object
        properties:
          replicas:
            type: integer
```

This lets Kubernetes validate the resource.

------------------------------------------------------------------------

# 8. Creating a CRD

Create a file:

``` text
database-crd.yaml
```

Example:

``` yaml
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition

metadata:
  name: databases.database.example.com

spec:
  group: database.example.com

  names:
    kind: Database
    plural: databases
    singular: database

  scope: Namespaced

  versions:
    - name: v1
      served: true
      storage: true

      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              type: object
              properties:
                engine:
                  type: string

                version:
                  type: string

                replicas:
                  type: integer
```

Apply it:

``` bash
kubectl apply -f database-crd.yaml
```

Verify:

``` bash
kubectl get crd
```

Expected output will contain something similar to:

``` text
NAME
databases.database.example.com
```

Inspect it:

``` bash
kubectl describe crd databases.database.example.com
```

# 11. Namespaced vs Cluster-Scoped Custom Resources

CRDs can define resources as either namespaced or cluster-scoped.

## 11.1 Namespaced

``` yaml
scope: Namespaced
```

Example:

``` yaml
apiVersion: database.example.com/v1
kind: Database
metadata:
  name: production-db
  namespace: production
```

The same resource name can exist in another namespace:

``` text
development/production-db
production/production-db
```

They are separate objects.

Use namespaced resources when the resource logically belongs to an
application or team namespace.

------------------------------------------------------------------------

## 11.2 Cluster-Scoped

``` yaml
scope: Cluster
```

A cluster-scoped custom resource does not belong to a namespace.

Example:

``` yaml
apiVersion: infrastructure.example.com/v1
kind: CloudAccount
metadata:
  name: aws-production
```

There is no:

``` yaml
namespace:
```

for the resource.

Use cluster scope when the resource represents something that logically
applies to the entire cluster.

------------------------------------------------------------------------

# 12. OpenAPI Schema and Validation

A major benefit of CRDs is schema validation.

Suppose your CRD defines:

``` yaml
replicas:
  type: integer
```

Then this is valid:

``` yaml
replicas: 3
```

But this is invalid:

``` yaml
replicas: "three"
```

You can define more constraints.

Example:

``` yaml
replicas:
  type: integer
  minimum: 1
  maximum: 10
```

Now Kubernetes can reject:

``` yaml
replicas: 0
```

and:

``` yaml
replicas: 20
```

------------------------------------------------------------------------

## Required Fields

You can define required fields:

``` yaml
required:
  - spec

properties:
  spec:
    type: object
    required:
      - engine
      - version
```

This means `engine` and `version` must be supplied.

------------------------------------------------------------------------

## Enum Values

You can restrict values:

``` yaml
engine:
  type: string
  enum:
    - postgres
    - mysql
    - mongodb
```

Then:

``` yaml
engine: postgres
```

is valid.

But:

``` yaml
engine: oracle
```

would fail validation.

------------------------------------------------------------------------

## String Constraints

You can define constraints such as:

``` yaml
version:
  type: string
  minLength: 1
```

------------------------------------------------------------------------

# 13. Defaulting

CRDs can provide default values.

Example:

``` yaml
replicas:
  type: integer
  default: 1
```

If the user writes:

``` yaml
spec:
  engine: postgres
```

the API can default:

``` yaml
replicas: 1
```

This is useful for simplifying resource manifests.

------------------------------------------------------------------------

# 14. Versioning Custom Resources

Custom APIs should be designed with versioning in mind.

Example:

``` text
database.example.com/v1alpha1
database.example.com/v1beta1
database.example.com/v1
```

A typical progression is:

``` text
v1alpha1
    ↓
v1beta1
    ↓
v1
```

Meaning:

### Alpha

Experimental.

The API may change significantly.

### Beta

More stable.

It may still change before becoming stable.

### Stable

Production-ready API.

------------------------------------------------------------------------

## `served`

Example:

``` yaml
served: true
```

This means that version is exposed through the Kubernetes API.

------------------------------------------------------------------------

## `storage`

Example:

``` yaml
storage: true
```

Exactly one version of a CRD should normally be the storage version.

The storage version is the version Kubernetes uses to persist objects.

------------------------------------------------------------------------

# 15. The Controller and Reconciliation

A CR by itself is just data stored through the Kubernetes API.

To make it useful for automation, we generally add a controller.

Consider:

``` yaml
kind: Database

spec:
  replicas: 3
```

The user is declaring:

> I want three database replicas.

The controller observes the CR and compares desired state with actual
state.

``` text
             Custom Resource
                    |
                    | desired state
                    v
             replicas = 3
                    |
                    v
              Controller
                    |
                    | observes
                    v
              Actual state
                    |
                    v
              replicas = 2
```

The controller creates or modifies resources until:

``` text
Desired State = Actual State
```

This is called **reconciliation**.

------------------------------------------------------------------------

# 16. Custom Resources Without a Controller

A CRD does not automatically create infrastructure.

Suppose you create:

``` yaml
apiVersion: database.example.com/v1
kind: Database

metadata:
  name: my-db

spec:
  engine: postgres
  replicas: 3
```

Kubernetes can store this object.

However, Kubernetes does not automatically know that:

``` text
Database
```

means:

``` text
Create PostgreSQL
Create PVC
Create Service
Configure replication
Perform backups
```

A controller must implement that behavior.

Therefore:

``` text
CRD
 |
 +-- Defines API
 |
 +-- Enables Kubernetes to store CRs
 |
 +-- Does NOT automatically implement application behavior
```

------------------------------------------------------------------------

A common architecture looks like this:

``` text
                 User
                  |
                  | kubectl apply
                  v
          +----------------+
          | Kubernetes API |
          |    Server      |
          +-------+--------+
                  |
                  v
          +----------------+
          | Custom Resource|
          |    Database    |
          +-------+--------+
                  |
                  | watch
                  v
          +----------------+
          |   Controller   |
          +-------+--------+
                  |
             reconcile
                  |
       +----------+----------+
       |          |          |
       v          v          v
```

-   ConfigMaps
-   Secrets
-   Services
-   Jobs

-   Deployments
-   StatefulSets
-   NetworkPolicies
-   monitoring resources

# 18. Operators

The Operator pattern extends the controller concept.

An Operator combines:

1.  Custom Resource Definitions
2.  Custom Resources
3.  Controllers
4.  Domain-specific operational knowledge

Example:

``` text
PostgreSQL Operator

CR:
  PostgreSQLCluster
        |
        v
    Controller
        |
        +--> StatefulSet
        +--> Service
        +--> PVC
        +--> Backup
        +--> Monitoring
        +--> Failover
```

Instead of users manually managing every underlying object, they
interact with the higher-level API.

For example:

``` yaml
apiVersion: database.example.com/v1
kind: PostgreSQLCluster

metadata:
  name: production

spec:
  version: "16"
  replicas: 3
  storage: 100Gi
```

The Operator handles the implementation details.

# 20. Status and Conditions

A well-designed Custom Resource normally has two important areas:

``` yaml
spec:
  ...

status:
  ...
```

## `spec`

Describes:

> What the user wants.

Example:

``` yaml
spec:
  replicas: 3
```

## `status`

Describes:

> What is currently happening.

Example:

``` yaml
status:
  readyReplicas: 3
  phase: Ready
```

A controller normally updates the status.

------------------------------------------------------------------------

## Conditions

Controllers often expose conditions such as:

``` yaml
status:
  conditions:
    - type: Ready
      status: "True"
      reason: DatabaseReady
      message: Database cluster is ready
```

Common condition types might include:

``` text
Ready
Available
Progressing
Degraded
```

The exact condition names depend on the API.

------------------------------------------------------------------------

# 21. Spec vs Status

This distinction is critical.

``` text
             Custom Resource
                  |
          +-------+-------+
          |               |
         spec           status
          |               |
          v               v
   Desired State     Observed State
          |               |
          |               |
     User changes      Controller
```

Example:

``` yaml
spec:
  replicas: 3
```

means:

> User wants three replicas.

While:

``` yaml
status:
  readyReplicas: 2
```

means:

> Controller currently observes two ready replicas.

The controller's job is to move:

``` text
status → desired spec
```

by reconciling the system.

------------------------------------------------------------------------

# 22. Labels, Annotations, and Finalizers

Custom Resources support normal Kubernetes metadata.

## Labels

Labels can be used for selection and organization.

Example:

``` yaml
metadata:
  labels:
    environment: production
    team: platform
```

------------------------------------------------------------------------

## Annotations

Annotations store additional metadata.

Example:

``` yaml
metadata:
  annotations:
    owner: platform-team
```

Annotations are not normally used for selecting resources.

------------------------------------------------------------------------

## Finalizers

Finalizers allow a controller to perform cleanup before an object is
actually deleted.

For example:

``` text
Delete Database CR
        |
        v
Controller sees deletion request
        |
        v
Backup / cleanup / external resource deletion
        |
        v
Remove finalizer
        |
        v
Resource is deleted
```

This is especially important when a Custom Resource represents something
outside Kubernetes.

Example:

``` text
Custom Resource
      |
      v
AWS RDS database
```

Deleting the CR might require the controller to decide whether the
external database should also be deleted.

------------------------------------------------------------------------

# 23. Custom Resource Lifecycle

A typical lifecycle looks like this:

``` text
1. Create CRD
       |
       v
2. Kubernetes registers new API resource
       |
       v
3. Create Custom Resource
       |
       v
4. API Server validates the object
       |
       v
5. Object is stored
       |
       v
6. Controller watches the object
       |
       v
7. Controller reconciles desired state
       |
       v
8. Controller creates/updates resources
       |
       v
9. Controller updates status
       |
       v
10. User observes status
```

When the CR is modified:

``` text
User changes spec
       |
       v
API Server
       |
       v
Controller receives event
       |
       v
Reconciliation
       |
       v
Actual state updated
```

# 24. Deleting CRDs

Be careful when deleting a CRD.

Example:

``` bash
kubectl delete crd databases.database.example.com
```

Deleting a CRD also affects the Custom Resources belonging to that
definition.

This is potentially destructive.

Before deleting a CRD, understand:

-   What CRs exist?
-   Does the controller depend on them?
-   Are external resources associated with them?
-   Are finalizers involved?
-   Is data stored outside Kubernetes?

Never casually delete a production CRD.

# 26. Complete Example

Let's build a simple `Database` CRD.

## Step 1 --- CRD

Create:

``` text
database-crd.yaml
```

``` yaml
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition

metadata:
  name: databases.database.example.com

spec:
  group: database.example.com

  names:
    kind: Database
    plural: databases
    singular: database

  scope: Namespaced

  versions:
    - name: v1
      served: true
      storage: true

      schema:
        openAPIV3Schema:
          type: object

          properties:
            spec:
              type: object

              properties:
                engine:
                  type: string
                  enum:
                    - postgres
                    - mysql

                version:
                  type: string

                replicas:
                  type: integer
                  minimum: 1
                  maximum: 10

              required:
                - engine
                - version
```

Apply:

``` bash
kubectl apply -f database-crd.yaml
```

Verify:

``` bash
kubectl get crd databases.database.example.com
```

------------------------------------------------------------------------

## Step 2 --- Create a Custom Resource

Create:

``` text
database.yaml
```

``` yaml
apiVersion: database.example.com/v1
kind: Database

metadata:
  name: production-db
  namespace: default

spec:
  engine: postgres
  version: "16"
  replicas: 3
```

Apply:

``` bash
kubectl apply -f database.yaml
```

------------------------------------------------------------------------

## Step 3 --- Verify

``` bash
kubectl get databases
```

Output:

``` text
NAME            AGE
production-db   10s
```

Inspect:

``` bash
kubectl get database production-db -o yaml
```

Describe:

``` bash
kubectl describe database production-db
```

------------------------------------------------------------------------

## Step 4 --- Understand What Has NOT Happened

At this point, Kubernetes has created/stored:

``` text
Database CR
```

But it has not automatically created:

``` text
PostgreSQL Pod
StatefulSet
Service
PVC
```

unless a controller exists to do so.

This is the most important practical distinction.

# 27. Best Practices

## 27.1 Use meaningful API groups

Prefer:

``` text
database.example.com
```

rather than something vague.

------------------------------------------------------------------------

## 27.2 Define a strong schema

Avoid accepting arbitrary structures when a well-defined schema is
possible.

Define:

-   Types
-   Required fields
-   Minimum/maximum values
-   Enum values
-   Defaults
-   Validation rules

------------------------------------------------------------------------

## 27.3 Design versioning early

Consider future evolution:

``` text
v1alpha1
v1beta1
v1
```

Avoid creating an API that is difficult to evolve.

------------------------------------------------------------------------

## 27.4 Keep `spec` and `status` separate

Use:

``` yaml
spec:
```

for desired state.

Use:

``` yaml
status:
```

for observed state.

------------------------------------------------------------------------

## 27.5 Make controllers idempotent

A controller may reconcile the same resource many times.

Therefore, reconciliation logic should safely produce the same desired
outcome when run repeatedly.

Conceptually:

``` text
Reconcile
   ↓
Create if missing
   ↓
Update if incorrect
   ↓
Do nothing if already correct
```

------------------------------------------------------------------------

## 27.6 Use conditions

Conditions make resource state easier to understand.

Example:

``` yaml
status:
  conditions:
    - type: Ready
      status: "True"
```

------------------------------------------------------------------------

## 27.7 Use finalizers carefully

Finalizers are powerful but can prevent deletion if the controller that
removes them is unavailable.

Always design cleanup behavior carefully.

------------------------------------------------------------------------

# 28. Common Mistakes

## Mistake 1: Thinking CRD creates infrastructure

Wrong:

``` text
CRD → automatically creates Pods
```

Correct:

``` text
CRD → defines API
CR → represents desired state
Controller → performs actions
```

------------------------------------------------------------------------

## Mistake 2: Confusing CR and CRD

Remember:

``` text
CRD = Definition
CR  = Instance
```

Similar to:

``` text
Class = Definition
Object = Instance
```

------------------------------------------------------------------------

## Mistake 3: Forgetting the API group

A CR normally contains:

``` yaml
apiVersion: database.example.com/v1
```

The API group and version must correspond to the CRD.

------------------------------------------------------------------------

## Mistake 4: Creating the CR before the CRD

If Kubernetes doesn't know the resource type, the CR cannot be created.

Correct order:

``` text
CRD
 ↓
CR
```

------------------------------------------------------------------------

## Mistake 5: Assuming a CRD is an Operator

A CRD only defines an API.

An Operator generally consists of:

``` text
CRD + Controller + Domain Knowledge
```

------------------------------------------------------------------------

## Mistake 6: Ignoring status

For controller-backed resources, status is extremely useful for
understanding what the controller has actually achieved.

------------------------------------------------------------------------

# 29. Troubleshooting

## Error: Resource type not found

Example:

``` text
the server doesn't have a resource type "databases"
```

Possible causes:

-   CRD is not installed.
-   CRD installation failed.
-   Wrong plural name.
-   Wrong API group/version.

Check:

``` bash
kubectl get crd
```

and:

``` bash
kubectl api-resources
```

------------------------------------------------------------------------

## Error: No matches for kind

Example:

``` text
no matches for kind "Database"
```

Check:

``` bash
kubectl get crd databases.database.example.com
```

Make sure your CR uses the correct:

``` yaml
apiVersion: database.example.com/v1
kind: Database
```

------------------------------------------------------------------------

## CR exists but nothing happens

This usually means the CRD exists, but there is no working
controller/operator.

Check:

``` bash
kubectl get pods
```

Look for the relevant controller.

Also inspect:

``` bash
kubectl describe database production-db
```

and controller logs.

For example:

``` bash
kubectl logs <controller-pod>
```

------------------------------------------------------------------------

## Resource stuck in Terminating

A finalizer may be preventing deletion.

Inspect:

``` bash
kubectl get database production-db -o yaml
```

Look for:

``` yaml
metadata:
  finalizers:
    - ...
```

Do not remove finalizers blindly in production. First determine why the
controller has not completed its cleanup.

------------------------------------------------------------------------

# 30. CR vs CRD vs Controller vs Operator

  -----------------------------------------------------------------------
  Concept                 Meaning                 Main Responsibility
  ----------------------- ----------------------- -----------------------
  CRD                     Custom Resource         Defines a new resource
                          Definition              type

  CR                      Custom Resource         Instance of the custom
                                                  resource

  Controller              Reconciliation logic    Makes actual state
                                                  match desired state

  Operator                Controller pattern with Manages complex
                          domain knowledge        applications/systems
  -----------------------------------------------------------------------

``` text
CRD
 ↓
"What does this resource look like?"

CR
 ↓
"What do I want?"

Controller
 ↓
"How do I make it happen?"

Operator
 ↓
"How do I manage this application like an expert?"
```

# 31. Interview Questions

## Q1. What is a Custom Resource?

A Custom Resource is an instance of a custom API type added to
Kubernetes.

------------------------------------------------------------------------

## Q2. What is a CRD?

A CustomResourceDefinition defines a new Kubernetes API resource type.

------------------------------------------------------------------------

## Q3. What is the difference between CR and CRD?

``` text
CRD = Definition
CR  = Instance
```

------------------------------------------------------------------------

## Q4. Does a CRD create Pods?

No.

A CRD only defines the API/resource type.

A controller or Operator can create Pods or other resources in response
to a CR.

------------------------------------------------------------------------

## Q5. What is a controller?

A controller continuously observes resources and reconciles actual state
toward desired state.

------------------------------------------------------------------------

## Q6. What is reconciliation?

Reconciliation is the process of comparing desired state with actual
state and taking corrective actions.

------------------------------------------------------------------------

## Q7. What is an Operator?

An Operator is a controller-based pattern that uses Kubernetes APIs to
automate operational tasks for a particular application or domain.

------------------------------------------------------------------------

## Q8. Can a CRD be namespaced?

A CRD itself is cluster-scoped, but the custom resources it defines can
be either:

``` text
Namespaced
```

or:

``` text
Cluster-scoped
```

depending on the CRD's `scope`.

------------------------------------------------------------------------

## Q9. What is `spec`?

`spec` describes desired state.

------------------------------------------------------------------------

## Q10. What is `status`?

`status` describes observed/current state and is normally maintained by
a controller.

------------------------------------------------------------------------

## Q11. What is a finalizer?

A finalizer allows a controller to perform cleanup before Kubernetes
completes deletion of an object.

------------------------------------------------------------------------

## Q12. How do you discover CRDs installed in a cluster?

``` bash
kubectl get crd
```

or:

``` bash
kubectl api-resources
```
------------------------------------------------------------------------

# 33. Summary

Custom Resources allow Kubernetes to be extended with new API objects.

The core concepts are:

``` text
CRD
 ↓
Defines a custom resource type

CR
 ↓
An instance of that custom resource

Controller
 ↓
Watches the CR and reconciles desired state

Operator
 ↓
Uses controllers and domain knowledge to manage complex systems
```

The complete model is:

``` text
                     Kubernetes API
                           |
                           v
                         CRD
                           |
                  Defines new resource
                           |
                           v
                          CR
                           |
                    Desired state
                           |
                           v
                      Controller
                           |
                     Reconciliation
                           |
              +------------+------------+
              |            |            |
              v            v            v
          Deployment    Service       PVC
              |
              v
             Pods
```

------------------------------------------------------------------------

## Quick Revision Cheat Sheet

``` text
CRD  → Defines a new Kubernetes API resource
CR   → Instance of that resource
Spec → Desired state
Status → Observed state
Controller → Reconciles desired and actual state
Operator → Controller + domain-specific operational knowledge
Finalizer → Cleanup before deletion
Schema → Defines/validates CR structure
Version → Allows API evolution
Scope → Namespaced or Cluster
```
