
## Network Policies & Pod Security Standards

> Comprehensive theory notes for learning, teaching, revision, and interview preparation.


# 1. Kubernetes Security Overview

Kubernetes security is not a single feature. It is a collection of controls that protect:

- The Kubernetes API
- Users and workloads
- Pods and containers
- Network communication
- Secrets
- Container images
- Nodes
- Runtime behavior

A useful mental model is:

```text
                    Kubernetes Security
                           |
       +-------------------+-------------------+
       |                   |                   |
 Authentication       Authorization       Admission
       |                   |                   |
    Who are you?       What can you do?    What can be created?
                           |
       +-------------------+-------------------+
       |                   |                   |
 Network Security     Pod Security       Data Security
       |                   |                   |
 NetworkPolicy          PSS/PSA          Secrets
```

Two important security mechanisms covered in these notes are:

```text
NetworkPolicy
    -> Controls network communication

Pod Security Standards
    -> Define security requirements for Pods
```

---

# 2. Network Policies

## 2.1 What is a NetworkPolicy?

A Kubernetes `NetworkPolicy` is an API object used to control network traffic to and from selected Pods.

It can control:

- Incoming traffic: Ingress
- Outgoing traffic: Egress
- Source Pods
- Source namespaces
- IP ranges
- Destination Pods
- Destination IP ranges
- Ports and protocols

The simplest mental model is:

> NetworkPolicy is a firewall-like mechanism for Pod network communication.

Example:

```text
Frontend Pod
     |
     | ALLOW
     v
Backend Pod
     |
     | ALLOW
     v
Database Pod
```

You might want:

```text
Frontend -> Backend       ALLOW
Backend  -> Database      ALLOW
Frontend -> Database      DENY
Internet -> Database      DENY
```

NetworkPolicy can express these requirements.

---

## 2.2 Why NetworkPolicy is Needed

By itself, Kubernetes networking does not provide application-level network authorization.

Consider:

```text
+-----------+       +-----------+       +-----------+
| Frontend  | ----> |  Backend  | ----> | Database  |
+-----------+       +-----------+       +-----------+
      |                   |                    |
      +-------------------+--------------------+
```

If the application architecture requires only:

```text
Frontend -> Backend
Backend  -> Database
```

then unnecessary communication should be restricted.

A compromised frontend should not automatically be able to communicate with the database.

This is an example of the **least-privilege principle**.

---

## 2.3 NetworkPolicy Architecture

A NetworkPolicy has three major concepts:

```text
                 NetworkPolicy
                      |
          +-----------+-----------+
          |           |           |
     Target Pods   Direction    Rules
          |           |           |
    podSelector    Ingress      from
                   Egress       to
```

A policy answers questions such as:

1. Which Pods are protected?
2. Is incoming or outgoing traffic being controlled?
3. Which sources are allowed?
4. Which destinations are allowed?
5. Which ports are allowed?

---

## 2.4 Basic NetworkPolicy Structure

Example:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy

metadata:
  name: backend-policy
  namespace: production

spec:
  podSelector:
    matchLabels:
      app: backend

  policyTypes:
    - Ingress
    - Egress

  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: frontend

  egress:
    - to:
        - podSelector:
            matchLabels:
              app: database
```

Breakdown:

```text
apiVersion
    -> NetworkPolicy API version

kind
    -> NetworkPolicy

metadata
    -> Name and namespace

spec
    -> Policy definition

podSelector
    -> Pods to which the policy applies

policyTypes
    -> Ingress and/or Egress

ingress
    -> Allowed incoming traffic

egress
    -> Allowed outgoing traffic
```

---

# 2.5 podSelector

`podSelector` identifies the Pods to which a NetworkPolicy applies.

Example:

```yaml
podSelector:
  matchLabels:
    app: backend
```

This selects Pods with:

```yaml
labels:
  app: backend
```

Example Pod:

```yaml
apiVersion: v1
kind: Pod

metadata:
  name: backend
  labels:
    app: backend

spec:
  containers:
    - name: backend
      image: nginx
```

The policy applies to this Pod.

### Empty podSelector

```yaml
podSelector: {}
```

means:

> Select all Pods in the policy's namespace.

Example:

```yaml
spec:
  podSelector: {}

  policyTypes:
    - Ingress
```

This targets every Pod in that namespace for ingress isolation.

---

# 2.6 Ingress and Egress

## Ingress

Ingress means incoming traffic.

```text
Client
   |
   | incoming traffic
   v
+------+
| Pod  |
+------+
```

Ingress answers:

> Who can connect to this Pod?

Example:

```yaml
ingress:
  - from:
      - podSelector:
          matchLabels:
            app: frontend
```

---

## Egress

Egress means outgoing traffic.

```text
+------+
| Pod  |
+------+
   |
   | outgoing traffic
   v
Database
```

Egress answers:

> Where can this Pod connect?

Example:

```yaml
egress:
  - to:
      - podSelector:
          matchLabels:
            app: database
```

---

# 2.7 policyTypes

`policyTypes` specifies which directions are being isolated by the policy.

### Ingress only

```yaml
policyTypes:
  - Ingress
```

### Egress only

```yaml
policyTypes:
  - Egress
```

### Both

```yaml
policyTypes:
  - Ingress
  - Egress
```

For a security design involving both directions, explicitly specifying both is usually clearer.

---

# 2.8 Ingress Rules

Example:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy

metadata:
  name: allow-frontend-to-backend

spec:
  podSelector:
    matchLabels:
      app: backend

  policyTypes:
    - Ingress

  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: frontend
```

Interpretation:

```text
Destination:
    backend Pods

Allowed source:
    frontend Pods
```

Traffic:

```text
Frontend ------> Backend
       ALLOWED
```

Other sources are not automatically allowed once the destination is isolated for ingress.

---

# 2.9 Egress Rules

Example:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy

metadata:
  name: allow-backend-to-database

spec:
  podSelector:
    matchLabels:
      app: backend

  policyTypes:
    - Egress

  egress:
    - to:
        - podSelector:
            matchLabels:
              app: database
```

Interpretation:

```text
Source:
    backend Pods

Allowed destination:
    database Pods
```

Traffic:

```text
Backend ------> Database
       ALLOWED
```

# 2.10 namespaceSelector

A `namespaceSelector` selects namespaces based on labels.

Example:

```yaml
namespaceSelector:
  matchLabels:
    environment: frontend
```

Suppose:

```text
Namespace: frontend
Label:
environment=frontend
```

Then a policy can allow traffic from Pods in that namespace.

Example:

```yaml
ingress:
  - from:
      - namespaceSelector:
          matchLabels:
            environment: frontend
```

---

## Combining namespaceSelector and podSelector

Example:

```yaml
ingress:
  - from:
      - namespaceSelector:
          matchLabels:
            environment: frontend
        podSelector:
          matchLabels:
            app: web
```

This means:

> Allow traffic from Pods labeled `app=web` in namespaces labeled `environment=frontend`.

The namespace and Pod conditions are combined for this peer.

---

# 2.11 ipBlock

`ipBlock` allows traffic from or to an IP CIDR range.

Example:

```yaml
ingress:
  - from:
      - ipBlock:
          cidr: 10.0.0.0/24
```

This allows traffic from:

```text
10.0.0.0 - 10.0.0.255
```

You can exclude a range:

```yaml
ipBlock:
  cidr: 10.0.0.0/16
  except:
    - 10.0.1.0/24
```

This means:

```text
Allow:
10.0.0.0/16

Except:
10.0.1.0/24
```

---

# 2.12 Ports and Protocols

NetworkPolicies can restrict traffic to specific ports.

Example:

```yaml
ingress:
  - from:
      - podSelector:
          matchLabels:
            app: frontend

    ports:
      - protocol: TCP
        port: 8080
```

Result:

```text
Frontend -> Backend:8080    ALLOW
Frontend -> Backend:3306    DENY
```

Common protocols:

```text
TCP
UDP
SCTP
```

Example:

```yaml
ports:
  - protocol: TCP
    port: 8080

  - protocol: TCP
    port: 8443
```

---

# 2.13 Default Deny

Default-deny policies are a common foundation for network segmentation.

## Default deny ingress

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy

metadata:
  name: default-deny-ingress

spec:
  podSelector: {}

  policyTypes:
    - Ingress
```

This selects all Pods in the namespace and isolates them from ingress traffic unless another applicable policy allows it.

Conceptually:

```text
Frontend ----X----> Backend
Other Pod ---X----> Backend
Internet ----X----> Backend
```

---

## Default deny egress

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy

metadata:
  name: default-deny-egress

spec:
  podSelector: {}

  policyTypes:
    - Egress
```

This restricts outgoing traffic from Pods in the namespace unless allowed by applicable policies.

---

## Default deny both

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy

metadata:
  name: default-deny-all

spec:
  podSelector: {}

  policyTypes:
    - Ingress
    - Egress
```

Conceptually:

```text
              Pod
             /   \
          DENY   DENY
           /       \
     Incoming     Outgoing
```

Explicit allow rules can then be added.

---

# 2.14 Allow Policies

After applying default deny, create explicit allow policies.

Example:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy

metadata:
  name: allow-frontend-to-backend

spec:
  podSelector:
    matchLabels:
      app: backend

  policyTypes:
    - Ingress

  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: frontend

      ports:
        - protocol: TCP
          port: 8080
```

Network architecture:

```text
Frontend
   |
   | TCP/8080
   | ALLOW
   v
Backend
```

---

# 2.15 Multiple NetworkPolicies

NetworkPolicies are additive.

Suppose two policies select the same Backend Pods:

```text
Policy A:
Frontend -> Backend

Policy B:
Monitoring -> Backend
```

The effective allowed sources include both:

```text
Frontend  -----> Backend   ALLOW
Monitoring -----> Backend  ALLOW
Other     --X--> Backend   DENY
```

NetworkPolicies are not normally processed as a simple first-match or top-to-bottom firewall rule list.

A useful mental model is:

> Applicable policies contribute allowed traffic.

---

# 2.16 NetworkPolicy and Services

A Service and NetworkPolicy solve different problems.

### Service

Provides:

- Stable virtual IP
- Service discovery
- Load balancing to selected Pods

### NetworkPolicy

Controls:

- Which network traffic is allowed

Example:

```text
Frontend
   |
   v
Service
   |
   v
Backend Pods
```

The Service determines how traffic reaches Backend Pods.

The NetworkPolicy determines whether that traffic is permitted.

---

# 2.17 NetworkPolicy and Ingress

Kubernetes Ingress and NetworkPolicy are also different.

### Ingress

Handles HTTP/HTTPS routing:

```text
Internet
   |
   v
Ingress
   |
   v
Service
   |
   v
Pod
```

### NetworkPolicy

Controls Pod network traffic:

```text
Frontend Pod
     |
     v
Backend Pod
```

Therefore:

```text
Ingress
    -> Routing

NetworkPolicy
    -> Traffic authorization
```

---

# 2.18 CNI Enforcement

Kubernetes defines the NetworkPolicy API, but network traffic enforcement is performed by the cluster networking implementation.

Examples of networking implementations with NetworkPolicy capabilities include:

- Cilium
- Calico
- Antrea
- Other compatible CNI implementations

Always verify that the CNI used by the cluster supports the policy features you depend on.

Creating a NetworkPolicy object does not by itself guarantee that every networking environment will enforce every desired behavior.

---

# 2.19 DNS and Egress

Egress policies can unintentionally block DNS.

A typical flow is:

```text
Backend Pod
    |
    | DNS query
    v
CoreDNS
```

If egress is restricted, DNS traffic may need to be explicitly permitted.

A typical example is:

```yaml
egress:
  - to:
      - namespaceSelector: {}
        podSelector:
          matchLabels:
            k8s-app: kube-dns

    ports:
      - protocol: UDP
        port: 53

      - protocol: TCP
        port: 53
```

Important:

> DNS Pod labels vary between cluster installations. Inspect your cluster before using a specific selector.

Useful command:

```bash
kubectl get pods -A --show-labels | grep -i dns
```

# 2.20 Three-Tier Example

Consider:

```text
                  Internet
                      |
                      v
                Load Balancer
                      |
                      v
                Frontend Pods
                      |
                      | 8080
                      v
                Backend Pods
                      |
                      | 5432
                      v
                Database Pods
```

Desired policy:

| Source | Destination | Port | Result |
|---|---|---:|---|
| Internet | Frontend | 80/443 | Allow according to ingress/network design |
| Frontend | Backend | 8080 | Allow |
| Backend | Database | 5432 | Allow |
| Frontend | Database | 5432 | Deny |
| Internet | Database | Any | Deny |
| Database | Frontend | Any | Deny |

Database policy:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy

metadata:
  name: database-policy

spec:
  podSelector:
    matchLabels:
      app: database

  policyTypes:
    - Ingress

  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: backend

      ports:
        - protocol: TCP
          port: 5432
```

# 2.21 NetworkPolicy Troubleshooting

When traffic unexpectedly fails, use this checklist:

```text
1. Identify source Pod
       |
2. Identify destination Pod
       |
3. Check destination Pod labels
       |
4. Check NetworkPolicies selecting destination
       |
5. Check whether ingress is isolated
       |
6. Check whether source is allowed
       |
7. Check destination port
       |
8. Check source egress policies
       |
9. Check DNS if names are used
       |
10. Verify CNI enforcement
```

Useful commands:

```bash
kubectl get networkpolicy -A
```

```bash
kubectl describe networkpolicy <name> -n <namespace>
```

```bash
kubectl get pods -n <namespace> --show-labels
```

```bash
kubectl get pods -n <namespace> -o wide
```

```bash
kubectl get namespace --show-labels
```

For testing, use temporary diagnostic Pods or images appropriate for your environment.

# 3. Pod Security Standards

## 3.1 What are Pod Security Standards?

Pod Security Standards (PSS) define security profiles for Kubernetes Pods.

They address questions such as:

- Can the container be privileged?
- Can the Pod use host namespaces?
- Can the workload run as root?
- Can dangerous Linux capabilities be added?
- Is privilege escalation allowed?
- Is seccomp configured?
- Can host filesystem paths be mounted?

Mental model:

```text
NetworkPolicy
    |
    +--> What network traffic can happen?

PSS
    |
    +--> What security configuration can the Pod use?
```

---

# 3.2 PSS vs NetworkPolicy

| Feature | NetworkPolicy | Pod Security Standards |
|---|---|---|
| Primary purpose | Network isolation | Pod security hardening |
| Controls | Network traffic | Pod security configuration |
| Ingress | Yes | No |
| Egress | Yes | No |
| Privileged containers | No | Yes |
| Linux capabilities | No | Yes |
| Non-root | No | Yes |
| Seccomp | No | Yes |
| Host namespaces | No | Yes |
| Main mechanism | NetworkPolicy API + CNI | PSS + PSA |

They complement each other.

---

# 3.3 Three PSS Profiles

Kubernetes defines three profiles:

```text
Privileged
    |
    v
Baseline
    |
    v
Restricted
```

They represent defined security profiles rather than generic numeric security scores.

| Profile | General purpose |
|---|---|
| Privileged | Unrestricted workloads |
| Baseline | Prevents common privilege-escalation configurations |
| Restricted | Strong workload hardening |

---

# 3.4 Privileged

The Privileged profile is effectively unrestricted by PSS.

It is intended for workloads that need elevated privileges.

Conceptually:

```text
Privileged
    |
    +-- Broad host interaction possible
    +-- Privileged containers possible
    +-- Broad security configuration possible
```

Use it only when the workload requirements justify the additional privileges.

---

# 3.5 Baseline

Baseline is intended to prevent known privilege-escalation mechanisms while supporting a broader set of workloads than Restricted.

Examples of configurations restricted by Baseline include:

- Privileged containers
- Certain host namespace configurations
- HostPath volumes
- Certain dangerous Linux capabilities
- Other known risky Pod settings

Baseline is useful when you need security controls but still have workloads that cannot meet all Restricted requirements.

---

# 3.6 Restricted

Restricted provides stronger security hardening.

It adds requirements around areas such as:

- Running as non-root
- Preventing privilege escalation
- Dropping capabilities
- Seccomp
- Allowed security configuration

A Restricted-style workload commonly looks like:

```yaml
securityContext:
  runAsNonRoot: true
  seccompProfile:
    type: RuntimeDefault
```

and at container level:

```yaml
securityContext:
  allowPrivilegeEscalation: false
  capabilities:
    drop:
      - ALL
```

The image must also support the required non-root execution model.

---

# 3.7 Pod Security Admission

Pod Security Standards define the profiles.

**Pod Security Admission (PSA)** is the Kubernetes admission mechanism that evaluates Pods against those profiles.

Conceptually:

```text
kubectl
   |
   v
API Server
   |
   v
Admission
   |
   v
Pod Security Admission
   |
   v
PSS evaluation
   |
   +----> Allow
   |
   +----> Warn
   |
   +----> Audit
   |
   +----> Reject
```

---

# 3.8 PSA Modes

There are three PSA modes:

```text
enforce
audit
warn
```

## enforce

Violating workloads are rejected.

```text
Pod
 |
 v
Policy violation
 |
 v
REJECT
```

## audit

The workload can be admitted, while the violation is recorded in audit information.

```text
Pod
 |
 v
Policy violation
 |
 +--> ADMIT
 |
 +--> Audit information
```

## warn

The workload can be admitted, but the user receives a warning.

```text
Pod
 |
 v
Policy violation
 |
 +--> ADMIT
 |
 +--> WARNING
```

---

# 3.9 Namespace Labels

PSA configuration is commonly applied through namespace labels.

Example:

```yaml
apiVersion: v1
kind: Namespace

metadata:
  name: production

  labels:
    pod-security.kubernetes.io/enforce: restricted
```

You can configure all three modes:

```yaml
metadata:
  labels:
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/audit: restricted
    pod-security.kubernetes.io/warn: restricted
```

# 3.11 SecurityContext

`securityContext` is the main Kubernetes configuration area for container and Pod security settings.

Example:

```yaml
spec:
  securityContext:
    runAsNonRoot: true
    seccompProfile:
      type: RuntimeDefault

  containers:
    - name: app
      image: example/app

      securityContext:
        allowPrivilegeEscalation: false

        capabilities:
          drop:
            - ALL
```

There can be:

```text
Pod securityContext
        |
        +-- Container securityContext
        |
        +-- Container securityContext
```

Pod-level and container-level settings have different scopes.

---

# 3.12 Non-Root Containers

Running applications as non-root is an important security practice.

Example:

```yaml
securityContext:
  runAsNonRoot: true
```

You can also specify a UID:

```yaml
securityContext:
  runAsUser: 1000
```

Conceptually:

```text
Less desirable:

Container
   |
   +-- UID 0
       root


Preferred where supported:

Container
   |
   +-- UID 1000
       application user
```

`runAsNonRoot` requires the image/runtime configuration to result in non-root execution.

---

# 3.13 Linux Capabilities

Linux capabilities split traditional root privileges into smaller units.

Examples include:

```text
CAP_NET_ADMIN
CAP_NET_RAW
CAP_SYS_ADMIN
CAP_SYS_PTRACE
```

A container can be configured to drop capabilities:

```yaml
securityContext:
  capabilities:
    drop:
      - ALL
```

Then only required capabilities should be added where justified.

Example:

```yaml
securityContext:
  capabilities:
    drop:
      - ALL
    add:
      - NET_BIND_SERVICE
```

The general security principle is:

> Grant only the capabilities the application actually requires.

---

# 3.14 Privilege Escalation

A container can be configured to prevent privilege escalation:

```yaml
securityContext:
  allowPrivilegeEscalation: false
```

Conceptually:

```text
Application
     |
     | Attempt to gain additional privileges
     v
   BLOCKED
```

This is an important control for hardened workloads.

---

# 3.15 Seccomp

`seccomp` stands for **Secure Computing Mode**.

It can restrict Linux system calls available to a process.

Conceptually:

```text
Application
    |
    v
Linux system calls
    |
    v
  seccomp
    |
 +--+---------+
 |            |
Allowed     Blocked
```

A common configuration is:

```yaml
securityContext:
  seccompProfile:
    type: RuntimeDefault
```

This uses the container runtime's default seccomp profile.

---

# 3.16 Host Namespaces

Pods can potentially share certain host namespaces.

Examples:

```yaml
hostNetwork: true
hostPID: true
hostIPC: true
```

These can weaken workload isolation.

### hostNetwork

```yaml
spec:
  hostNetwork: true
```

The Pod uses the host network namespace.

### hostPID

```yaml
spec:
  hostPID: true
```

The Pod can share the host process namespace.

### hostIPC

```yaml
spec:
  hostIPC: true
```

The Pod can share the host IPC namespace.

Baseline and Restricted place restrictions on these host namespace configurations.

---

# 3.17 HostPath

`hostPath` mounts a path from the Kubernetes node into a Pod.

Example:

```yaml
volumes:
  - name: host-data
    hostPath:
      path: /etc
```

This can expose host filesystem resources to the container.

Because of the isolation implications, hostPath is restricted by the more secure PSS profiles.

---

# 3.18 Example of a Hardened Pod

A simplified Restricted-compatible security configuration is:

```yaml
apiVersion: v1
kind: Pod

metadata:
  name: secure-app
  namespace: secure-apps

spec:
  securityContext:
    runAsNonRoot: true

    seccompProfile:
      type: RuntimeDefault

  containers:
    - name: app
      image: <non-root-compatible-image>

      securityContext:
        allowPrivilegeEscalation: false

        capabilities:
          drop:
            - ALL
```

Important:

> Replace the placeholder image with an image designed to run as a non-root user.

# 3.20 Testing an Insecure Pod

Example:

```yaml
apiVersion: v1
kind: Pod

metadata:
  name: insecure-pod
  namespace: secure-apps

spec:
  containers:
    - name: app
      image: nginx

      securityContext:
        privileged: true
```

With Restricted enforcement, this configuration violates the applicable Pod Security Standard and should be rejected.

The exact error output will identify the violated policy requirement.

# 3.21 Migration Strategy

Do not blindly enable strict enforcement on an existing production environment.

A safer rollout pattern is:

```text
Existing workloads
       |
       v
      WARN
       |
       v
Identify violations
       |
       v
Fix workloads
       |
       v
      AUDIT
       |
       v
Validate
       |
       v
    ENFORCE
```

Example initial configuration:

```yaml
metadata:
  labels:
    pod-security.kubernetes.io/warn: restricted
```

After workloads are remediated:

```yaml
metadata:
  labels:
    pod-security.kubernetes.io/enforce: restricted
```

# 3.22 PSS Troubleshooting

When a Pod is rejected:

### Step 1: Check namespace labels

```bash
kubectl get namespace <namespace> --show-labels
```

### Step 2: Identify the configured profile

Look for:

```text
pod-security.kubernetes.io/enforce
pod-security.kubernetes.io/audit
pod-security.kubernetes.io/warn
```

### Step 3: Inspect the Pod manifest

```bash
kubectl get pod <pod> -o yaml
```

Or inspect the Deployment:

```bash
kubectl get deployment <deployment> -o yaml
```

### Step 4: Check securityContext

Look for:

```text
privileged
runAsUser
runAsNonRoot
allowPrivilegeEscalation
capabilities
seccompProfile
```

### Step 5: Read the admission error

PSA messages generally identify the relevant restricted field or control.

# 4. NetworkPolicy vs PSS

This distinction is essential.

| Question | NetworkPolicy | PSS |
|---|---|---|
| Who can connect to the Pod? | Yes | No |
| Where can the Pod connect? | Yes | No |
| Can container be privileged? | No | Yes |
| Can Pod use hostNetwork? | No | Yes |
| Can dangerous capabilities be added? | No | Yes |
| Can workload run as root? | No | Yes |
| Can privilege escalation be disabled? | No | Yes |
| Seccomp configuration | No | Yes |
| Main concern | Network | Workload security |

Simple rule:

```text
NetworkPolicy
    = Network security

PSS
    = Pod/workload security
```

# 5. Layered Kubernetes Security

Neither NetworkPolicy nor PSS should be treated as a complete security solution.

A layered model is:

```text
+--------------------------------------+
| Application Security                 |
+--------------------------------------+
| Image & Supply Chain Security        |
+--------------------------------------+
| Pod Security Standards / PSA         |
+--------------------------------------+
| NetworkPolicy                        |
+--------------------------------------+
| RBAC                                 |
+--------------------------------------+
| Secrets Management                   |
+--------------------------------------+
| Node / OS Security                   |
+--------------------------------------+
| Cloud / Infrastructure Security      |
+--------------------------------------+
```

Important Kubernetes security areas include:

### Authentication

Who are you?

### Authorization

What are you allowed to do?

Usually implemented with RBAC.

### Admission

Should this object be allowed into the cluster?

PSA is one admission control mechanism.

### Network security

Who can communicate with whom?

NetworkPolicy.

### Pod security

What privileges can a workload have?

PSS/PSA and securityContext.

### Secrets

How are credentials and sensitive values protected?

### Image security

Are images trusted and free of known vulnerabilities?

### Runtime security

What happens after the workload starts?

# 6. Production Security Patterns

## Pattern 1: Default deny networking

Start with:

```text
Default DENY
      |
      v
Explicit ALLOW
```

For example:

```text
Frontend -> Backend
Backend  -> Database
Backend  -> DNS
```

Only required communication is permitted.

---

## Pattern 2: Restricted Pod security

Where workloads support it:

```text
Restricted
   |
   +-- Non-root
   +-- No privilege escalation
   +-- Drop unnecessary capabilities
   +-- RuntimeDefault seccomp
   +-- Avoid host namespaces
   +-- Avoid hostPath
```

---

## Pattern 3: Separate namespaces

Use namespaces to provide organizational and security boundaries:

```text
production
staging
development
monitoring
security
```

Apply appropriate policies per namespace.

---

## Pattern 4: Least privilege

Apply least privilege at multiple levels:

```text
RBAC
  -> Minimum Kubernetes permissions

NetworkPolicy
  -> Minimum network access

PSS
  -> Minimum Pod privileges

Linux capabilities
  -> Minimum kernel privileges
```

---

## Pattern 5: Progressive PSS rollout

Use:

```text
WARN
  |
AUDIT
  |
ENFORCE
```

This reduces the risk of unexpectedly breaking existing workloads.

# 7. Interview Questions

## NetworkPolicy

### Q1. What is a NetworkPolicy?

A Kubernetes API object used to control network traffic to and from selected Pods.

### Q2. What are the two main traffic directions?

```text
Ingress
Egress
```

### Q3. What does `podSelector` do?

Selects Pods to which the policy applies or, in a peer rule, identifies Pods participating in allowed traffic.

### Q4. What does an empty `podSelector` mean?

When used as the policy's top-level selector:

```yaml
podSelector: {}
```

it selects all Pods in the policy's namespace.

### Q5. What is `namespaceSelector`?

Selects namespaces based on namespace labels.

### Q6. What is `ipBlock`?

Specifies an IP CIDR range as a traffic source or destination.

### Q7. Are NetworkPolicies first-match rules?

No. Applicable NetworkPolicies are additive; allowed traffic from applicable policies contributes to the effective allowed set.

### Q8. Does Kubernetes itself enforce every NetworkPolicy?

Enforcement is provided by the cluster's networking implementation/CNI. Verify the CNI supports the features being used.

### Q9. Can NetworkPolicy control ports?

Yes.

Example:

```yaml
ports:
  - protocol: TCP
    port: 8080
```

### Q10. Can NetworkPolicy control DNS?

Egress policies can affect DNS. If egress is restricted, DNS traffic may need to be explicitly allowed.

---

## Pod Security Standards

### Q11. What are Pod Security Standards?

Defined Kubernetes security profiles that specify security requirements for Pods.

### Q12. What are the three PSS profiles?

```text
Privileged
Baseline
Restricted
```

### Q13. What is Pod Security Admission?

The Kubernetes admission mechanism that evaluates Pods against Pod Security Standards.

### Q14. What are the three PSA modes?

```text
enforce
audit
warn
```

### Q15. What happens in enforce mode?

A violating Pod is rejected.

### Q16. What happens in warn mode?

The Pod can be admitted, but the user receives a warning.

### Q17. What happens in audit mode?

The Pod can be admitted, while the violation is recorded in audit information.

### Q18. What replaced PodSecurityPolicy?

PodSecurityPolicy was deprecated in Kubernetes 1.21 and removed in Kubernetes 1.25. Pod Security Standards and Pod Security Admission provide the modern built-in approach.

### Q19. Does PSS replace NetworkPolicy?

No.

```text
PSS
 -> Pod security configuration

NetworkPolicy
 -> Network traffic
```

### Q20. What is `runAsNonRoot`?

A securityContext setting that requires the container to run as a non-root user.

### Q21. What is seccomp?

A Linux security mechanism that can restrict the system calls available to a process.

### Q22. Why drop Linux capabilities?

To reduce the privileges available to a container to only those it needs.
