# Kubernetes ConfigMaps and Secrets

# 1. Introduction

Applications running in Kubernetes frequently need configuration values such as:

- Database host
- Database port
- Application environment
- Log level
- Feature flags
- API endpoints
- Usernames
- Passwords
- API tokens
- TLS certificates

A common but poor approach is to hardcode these values inside the application image or directly inside a Deployment.

Kubernetes provides two important objects for externalizing configuration:

```text
                  Kubernetes Configuration
                           |
                 +---------+---------+
                 |                   |
                 v                   v
             ConfigMap            Secret
                 |                   |
        Non-sensitive data      Sensitive data
```

### ConfigMap

A **ConfigMap** stores non-confidential configuration data.

Examples:

```text
APP_ENV=production
LOG_LEVEL=info
DB_HOST=mysql
DB_PORT=3306
```

### Secret

A **Secret** stores sensitive data such as:

```text
DB_USERNAME
DB_PASSWORD
API_TOKEN
TLS_PRIVATE_KEY
```

---

# 2. Why Configuration Management?

Consider an application image:

```text
myapp:v1
```

The same image might be deployed into:

```text
Development
Testing
Production
```

Each environment may require different configuration.

For example:

```text
Development
DB_HOST=dev-mysql

Testing
DB_HOST=test-mysql

Production
DB_HOST=prod-mysql
```

If these values are baked into the container image, a different image may need to be built for every environment.

Instead:

```text
                 Application Image
                     myapp:v1
                         |
             +-----------+-----------+
             |                       |
             v                       v
        ConfigMap                 Secret
             |                       |
       Environment config       Credentials
             |                       |
             +-----------+-----------+
                         |
                         v
                        Pod
```

The application image remains reusable while configuration can change independently.

# 3. ConfigMaps

A ConfigMap is a Kubernetes API object used to store **non-confidential configuration data** as key-value pairs or configuration files.

Basic example:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config

data:
  APP_NAME: VotingApp
  APP_ENV: production
  LOG_LEVEL: info
  DB_HOST: mysql
  DB_PORT: "3306"
```

Apply it:

```bash
kubectl apply -f configmap.yaml
```

Check it:

```bash
kubectl get configmap
```

or:

```bash
kubectl get cm
```

Inspect it:

```bash
kubectl describe configmap app-config
```

Get the complete YAML:

```bash
kubectl get configmap app-config -o yaml
```

---

# 4. Creating ConfigMaps

There are several ways to create a ConfigMap.

## 4.1 Create from YAML

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config

data:
  APP_ENV: production
  LOG_LEVEL: info
```

```bash
kubectl apply -f configmap.yaml
```

---

## 4.2 Create from literals

```bash
kubectl create configmap app-config \
  --from-literal=APP_ENV=production \
  --from-literal=LOG_LEVEL=info
```

Verify:

```bash
kubectl get configmap app-config -o yaml
```

---

## 4.3 Create from a file

Suppose:

```text
application.properties
```

contains:

```properties
APP_NAME=VotingApp
APP_ENV=production
LOG_LEVEL=info
```

Create the ConfigMap:

```bash
kubectl create configmap app-config \
  --from-file=application.properties
```

---

## 4.4 Create from an entire directory

```bash
kubectl create configmap app-config \
  --from-file=config/
```

Kubernetes creates entries based on the files in the directory.

# 5. Using ConfigMaps in Pods

A ConfigMap can be consumed by a Pod in several ways.

The most common approaches are:

```text
ConfigMap
   |
   +----> Environment variables
   |
   +----> Individual environment variable
   |
   +----> Volume-mounted files
```

---

## 5.1 Using `envFrom`

`envFrom` imports all suitable keys from the ConfigMap as environment variables.

ConfigMap:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config

data:
  APP_ENV: production
  LOG_LEVEL: info
  DB_HOST: mysql
```

Deployment:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: backend

spec:
  replicas: 2

  selector:
    matchLabels:
      app: backend

  template:
    metadata:
      labels:
        app: backend

    spec:
      containers:
        - name: backend
          image: my-backend:v1

          envFrom:
            - configMapRef:
                name: app-config
```

The container receives:

```text
APP_ENV=production
LOG_LEVEL=info
DB_HOST=mysql
```

---

## 5.2 Using `configMapKeyRef`

Sometimes you only want one specific key.

```yaml
env:
  - name: APPLICATION_ENV
    valueFrom:
      configMapKeyRef:
        name: app-config
        key: APP_ENV
```

Here:

```text
ConfigMap
   |
   +-- APP_ENV ----------> APPLICATION_ENV
   |
   +-- LOG_LEVEL
   |
   +-- DB_HOST
```

Only `APP_ENV` is consumed.

---

## 5.3 `env` vs `envFrom`

### `env`

Used when you want specific keys.

```yaml
env:
  - name: DB_HOST
    valueFrom:
      configMapKeyRef:
        name: app-config
        key: DB_HOST
```

### `envFrom`

Used when you want to import multiple keys.

```yaml
envFrom:
  - configMapRef:
      name: app-config
```

Mental model:

```text
env
 |
 +---- Select specific keys


envFrom
 |
 +---- Import configuration from the referenced object
```

---

# 6. ConfigMaps as Volumes

ConfigMaps can also be mounted as files inside a container.

This is especially useful when an application expects a configuration file.

Example:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config

data:
  application.properties: |
    APP_NAME=VotingApp
    APP_ENV=production
    LOG_LEVEL=info
```

Pod:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: config-demo

spec:
  containers:
    - name: app
      image: nginx

      volumeMounts:
        - name: config-volume
          mountPath: /etc/app/config

  volumes:
    - name: config-volume
      configMap:
        name: app-config
```

Inside the container:

```bash
kubectl exec -it config-demo -- bash
```

Then:

```bash
ls /etc/app/config
```

You can access:

```text
application.properties
```

Read it:

```bash
cat /etc/app/config/application.properties
```

---

## 6.1 Mounting a specific ConfigMap key

Suppose the ConfigMap contains:

```yaml
data:
  app.conf: |
    server.port=8080
```

You can mount it using `subPath`:

```yaml
volumeMounts:
  - name: config-volume
    mountPath: /etc/app/app.conf
    subPath: app.conf
```

---

# 7. Updating ConfigMaps

Suppose the ConfigMap initially contains:

```text
LOG_LEVEL=info
```

You update it to:

```text
LOG_LEVEL=debug
```

What happens?

The answer depends on how the ConfigMap is consumed.

---

## 7.1 ConfigMap used as an environment variable

If the ConfigMap was injected as an environment variable:

```yaml
envFrom:
  - configMapRef:
      name: app-config
```

the environment variable in an already-running container does **not automatically change**.

A Pod restart is normally required.

For a Deployment:

```bash
kubectl rollout restart deployment backend
```

Then the newly created Pods receive the new value.

---

## 7.2 ConfigMap mounted as a volume

For a ConfigMap mounted as a volume, Kubernetes can update the mounted files after the ConfigMap changes, subject to the kubelet's update mechanism.

However, the application itself must notice and reload the changed configuration if it needs the new value immediately.

Therefore:

```text
ConfigMap updated
       |
       v
Mounted file may update
       |
       v
Application must reload/read it
```

Do not assume that changing a mounted configuration file automatically causes the application process to restart or reload.

# 8. Secrets

A Kubernetes Secret is an object intended to hold **small amounts of sensitive data**, such as:

- Passwords
- API tokens
- Access keys
- SSH keys
- TLS certificates
- Registry credentials

Example:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-secret

type: Opaque

stringData:
  DB_USERNAME: admin
  DB_PASSWORD: MySecretPassword
```

Apply:

```bash
kubectl apply -f secret.yaml
```

Check:

```bash
kubectl get secrets
```

Example output:

```text
NAME         TYPE     DATA
db-secret    Opaque   2
```

Inspect metadata:

```bash
kubectl describe secret db-secret
```

---

# 9. Creating Secrets

## 9.1 Using `stringData`

`stringData` allows you to write secret values as strings in the manifest.

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-secret

type: Opaque

stringData:
  username: admin
  password: MySecretPassword
```

This is convenient when creating a manifest.

---

## 9.2 Using `data`

The `data` field expects Base64-encoded values.

Example:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-secret

type: Opaque

data:
  username: YWRtaW4=
  password: TXlTZWNyZXRQYXNzd29yZA==
```

Decode a value:

```bash
echo 'TXlTZWNyZXRQYXNzd29yZA==' | base64 --decode
```

Output:

```text
MySecretPassword
```

### Important

Base64 is **encoding**, not encryption.

```text
Base64 != Encryption
```

This is one of the most important concepts to understand about Kubernetes Secrets.

---

## 9.3 Create a generic Secret from literals

```bash
kubectl create secret generic db-secret \
  --from-literal=DB_USERNAME=admin \
  --from-literal=DB_PASSWORD=MySecretPassword
```

Verify:

```bash
kubectl get secret db-secret
```

---

## 9.4 Create a Secret from files

```bash
kubectl create secret generic app-secret \
  --from-file=./credentials.txt
```

---

# 10. Using Secrets in Pods

Secrets can be consumed in the same general ways as ConfigMaps:

```text
Secret
  |
  +----> Environment variables
  |
  +----> Volume-mounted files
```

---

## 10.1 Using `secretKeyRef`

To inject one key:

```yaml
env:
  - name: DB_PASSWORD
    valueFrom:
      secretKeyRef:
        name: db-secret
        key: DB_PASSWORD
```

Inside the application:

```text
DB_PASSWORD=<secret value>
```

---

## 10.2 Using `envFrom`

To import all suitable keys:

```yaml
envFrom:
  - secretRef:
      name: db-secret
```

For example, if the Secret contains:

```text
DB_USERNAME
DB_PASSWORD
```

both can be made available as environment variables.

---

## 10.3 Complete example

Secret:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-secret

type: Opaque

stringData:
  DB_USERNAME: admin
  DB_PASSWORD: MySecretPassword
```

Deployment:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: backend

spec:
  replicas: 2

  selector:
    matchLabels:
      app: backend

  template:
    metadata:
      labels:
        app: backend

    spec:
      containers:
        - name: backend
          image: my-backend:v1

          env:
            - name: DB_USERNAME
              valueFrom:
                secretKeyRef:
                  name: db-secret
                  key: DB_USERNAME

            - name: DB_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: db-secret
                  key: DB_PASSWORD
```

---

# 11. Secrets as Volumes

Secrets can also be mounted as files.

Example:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: secret-demo

spec:
  containers:
    - name: app
      image: nginx

      volumeMounts:
        - name: secret-volume
          mountPath: /etc/secrets
          readOnly: true

  volumes:
    - name: secret-volume
      secret:
        secretName: db-secret
```

Inside the container:

```bash
ls /etc/secrets
```

You may see:

```text
DB_USERNAME
DB_PASSWORD
```

Read a value:

```bash
cat /etc/secrets/DB_PASSWORD
```

# 12. Secret Types

Kubernetes supports different Secret types.

## 12.1 Opaque

Generic Secret:

```yaml
type: Opaque
```

Used for:

```text
Passwords
API tokens
Credentials
Application secrets
```

---

## 12.2 TLS

Used for TLS certificates:

```yaml
type: kubernetes.io/tls
```

Typically contains:

```text
tls.crt
tls.key
```

Example:

```bash
kubectl create secret tls app-tls \
  --cert=tls.crt \
  --key=tls.key
```

---

## 12.3 Docker registry credentials

Used to authenticate to a private container registry:

```yaml
type: kubernetes.io/dockerconfigjson
```

Create:

```bash
kubectl create secret docker-registry regcred \
  --docker-server=registry.example.com \
  --docker-username=myuser \
  --docker-password=mypassword
```

Use it in a Pod:

```yaml
spec:
  imagePullSecrets:
    - name: regcred
```

This allows Kubernetes to authenticate when pulling a private image.

# 13. ConfigMap vs Secret

| Feature | ConfigMap | Secret |
|---|---|---|
| Primary purpose | Non-sensitive configuration | Sensitive configuration |
| Passwords | No | Yes |
| API tokens | No | Yes |
| DB host | Yes | Usually no |
| Log level | Yes | No |
| Environment variables | Yes | Yes |
| Volume mounts | Yes | Yes |
| Namespace scoped | Yes | Yes |
| Base64 requirement | No | `data` values use Base64 |
| Encryption | Not intended for secrecy | Requires appropriate storage protection |
| RBAC important | Yes | Extremely important |

The easiest mental model:

```text
              Configuration
                    |
           +--------+--------+
           |                 |
           v                 v
     Non-sensitive        Sensitive
           |                 |
           v                 v
      ConfigMap            Secret
```

# 14. Security Considerations

Secrets deserve special attention.

## 14.1 Base64 is not encryption

This:

```text
TXlTZWNyZXRQYXNzd29yZA==
```

can be decoded easily.

Therefore:

```text
Base64 encoding
       ≠
Encryption
```

Do not put a password into Base64 and assume it is secure.

---

## 14.2 Encryption at rest

Kubernetes can be configured to encrypt Secret data at rest in the cluster's backing storage.

Conceptually:

```text
Secret
   |
   v
Kubernetes API
   |
   v
Encryption at rest
   |
   v
etcd
```

For production clusters, administrators should understand and configure appropriate encryption-at-rest protection.

Managed Kubernetes platforms may provide platform-specific mechanisms for this.

---

## 14.3 RBAC

RBAC controls which identities can access Kubernetes resources.

For example:

```text
User / ServiceAccount
        |
        v
       RBAC
        |
        +---- Can get Secret?
        |
        +---- Can list Secret?
        |
        +---- Can watch Secret?
```

Avoid giving broad Secret permissions unnecessarily.

The principle should be:

```text
Least privilege
```

A workload should have access only to the Secrets it actually needs.

---

## 14.4 Avoid logging secrets

Do not do:

```bash
echo $DB_PASSWORD
```

in production troubleshooting unless there is a controlled reason.

Applications should also avoid logging:

```text
Passwords
API tokens
Access keys
Private keys
```

---

## 14.5 Environment variables vs mounted Secret files

Environment variables are convenient:

```yaml
env:
  - name: DB_PASSWORD
    valueFrom:
      secretKeyRef:
        name: db-secret
        key: DB_PASSWORD
```

But applications and diagnostic tooling may expose environment variables unintentionally.

A file-based approach can be useful for credentials and certificates:

```text
/etc/secrets/db-password
/etc/secrets/tls.key
```

The right choice depends on how the application consumes credentials.

# 15. Namespaces and Access

ConfigMaps and Secrets are namespace-scoped.

For example:

```text
Namespace: development
----------------------
Pod
ConfigMap
Secret
```

and:

```text
Namespace: production
---------------------
Pod
ConfigMap
Secret
```

A Pod in the `production` namespace does not simply reference a Secret in `development`.

You normally create/reference the required object in the same namespace.

This is another reason namespaces are useful for organizing and isolating workloads.

# 16. Real-World Architecture

A typical application can look like this:

```text
                     Kubernetes Cluster
                            |
              +-------------+-------------+
              |                           |
              v                           v
          ConfigMap                    Secret
              |                           |
              |                           |
              +-------------+-------------+
                            |
                            v
                       Deployment
                            |
                            v
                           Pods
                            |
                            v
                       Application
```

For example:

### ConfigMap

```text
APP_ENV=production
DB_HOST=mysql
DB_PORT=3306
LOG_LEVEL=info
```

### Secret

```text
DB_USERNAME=admin
DB_PASSWORD=<secret>
```

### Pod

The application receives:

```text
Configuration:
    APP_ENV
    DB_HOST
    DB_PORT
    LOG_LEVEL

Credentials:
    DB_USERNAME
    DB_PASSWORD
```

The container image itself does not need to contain environment-specific configuration.

# 17. Common Mistakes

## Mistake 1: Password inside ConfigMap

Avoid:

```yaml
kind: ConfigMap

data:
  DB_PASSWORD: MyPassword
```

Use a Secret instead.

---

## Mistake 2: Thinking Base64 protects a password

Incorrect:

```text
Base64 = secure encryption
```

Correct:

```text
Base64 = encoding
```

---

## Mistake 3: Hardcoding configuration into the image

Avoid building:

```text
myapp-production:v1
myapp-testing:v1
myapp-development:v1
```

just because configuration changes.

Prefer:

```text
One application image
        +
Environment-specific configuration
```

---

## Mistake 4: Assuming environment variables update automatically

If a ConfigMap or Secret is injected as an environment variable, changing the object does not change the existing process environment.

A Pod restart is normally required.

---

## Mistake 5: Giving excessive Secret permissions

Avoid broad permissions such as allowing every workload or user to read every Secret.

Use RBAC and least privilege.

---

## Mistake 6: Putting large application artifacts into ConfigMaps

ConfigMaps are intended for configuration, not for storing large application files, databases, or general-purpose artifacts.

---

# 18. Best Practices

### ConfigMaps

Use ConfigMaps for:

- Environment-specific configuration
- Application settings
- Feature flags
- Service endpoints
- Log configuration
- Configuration files

### Secrets

Use Secrets for:

- Passwords
- API tokens
- Credentials
- TLS keys and certificates
- Registry credentials

### Security

Use:

```text
RBAC
+
Least privilege
+
Encryption at rest
+
Secure Secret management
+
Avoid secret logging
```

For larger production environments, consider integrating Kubernetes with an external Secret-management system rather than treating Kubernetes Secret manifests as the complete credential-management solution.
