# Kubernetes Objects, YAML, Pods & Deployments

## 1. Kubernetes Objects

A **Kubernetes object** is a persistent representation of a resource that Kubernetes manages.

Common objects include:

- Pod
- ReplicaSet
- Deployment
- Service
- Namespace
- ConfigMap
- Secret
- StatefulSet
- DaemonSet
- Job
- CronJob

When you create an object, you are declaring the state you want Kubernetes to maintain.

```text
Desired State
      ↓
Kubernetes
      ↓
Actual State
      ↓
Reconciliation
      ↺
```

---

## 2. Kubernetes YAML

Kubernetes objects are commonly defined using YAML manifests.

Example:

```yaml
apiVersion: v1
kind: Pod

metadata:
  name: nginx

spec:
  containers:
    - name: nginx
      image: nginx
```

The four fields to understand first are:

```text
apiVersion
kind
metadata
spec
```

### apiVersion

Specifies the API group/version used for the resource.

Examples:

```yaml
apiVersion: v1
```

```yaml
apiVersion: apps/v1
```

```yaml
apiVersion: batch/v1
```

```yaml
apiVersion: networking.k8s.io/v1
```

It identifies the API group/version for the resource; it is not simply the Kubernetes software version.

### kind

Specifies the type of object.

```yaml
kind: Pod
```

```yaml
kind: Deployment
```

```yaml
kind: Service
```

### metadata

Identifies and describes the object.

```yaml
metadata:
  name: nginx
  namespace: production
  labels:
    app: nginx
    environment: production
```

Important metadata fields include:

- `name`
- `namespace`
- `labels`
- `annotations`

### spec

Defines the desired configuration.

For a Pod:

```yaml
spec:
  containers:
    - name: nginx
      image: nginx
```

For a Deployment:

```yaml
spec:
  replicas: 3
```

Think:

```text
spec → What I want Kubernetes to maintain
```

### status

Kubernetes maintains status information describing observed state.

Conceptually:

```text
spec
 ↓
Desired State

status
 ↓
Observed State
```

---

## 3. Declarative Kubernetes

Kubernetes is primarily declarative.

### Imperative

You specify actions:

```text
Start container 1
Start container 2
Start container 3
```

### Declarative

You specify the desired result:

```yaml
spec:
  replicas: 3
```

Kubernetes determines the actions required to reach that state.

```text
YAML
 ↓
Desired State
 ↓
Kubernetes API
 ↓
Controllers
 ↓
Actual State
```

# 5. Pods

## What Is a Pod?

A **Pod is the smallest deployable unit in Kubernetes**.

A Pod represents one or more containers that are managed together.

The most common case is a single application container:

```text
Pod
 │
 └── Application Container
```

A Pod can also contain multiple tightly coupled containers:

```text
Pod
 │
 ├── Application Container
 │
 └── Sidecar Container
```

---

## Why Does Kubernetes Use Pods?

Containers inside the same Pod:

- Are scheduled together.
- Share the Pod's network namespace.
- Can communicate using `localhost`.
- Can share volumes when configured.

Conceptually:

```text
              Pod
               │
       ┌───────┴────────┐
       │                │
   Application       Sidecar
    Container        Container
       │                │
       └── localhost ───┘
```

The Pod is therefore the unit Kubernetes schedules and manages, rather than an individual container.

---

## Pod Networking

A Pod receives an IP address.

Containers within the same Pod share the Pod's network namespace.

```text
Pod IP: 10.10.1.20

┌─────────────────────────────┐
│             Pod             │
│                             │
│  nginx :80                  │
│  sidecar :8080              │
│                             │
│  Shared network namespace   │
└─────────────────────────────┘
```

Because they share the network namespace, containers in the same Pod can generally communicate through:

```text
localhost
```

---

## Pod Lifecycle

At a high level, a Pod can move through phases such as:

```text
Pending
   ↓
Running
   ↓
Succeeded
```

or:

```text
Pending
   ↓
Running
   ↓
Failed
```

Containers inside Pods also have individual states such as:

```text
Waiting
Running
Terminated
```

Pod phase and container state are related but are not the same thing.

# 6. Why We Don't Usually Manage Pods Directly

Suppose you create one Pod:

```text
Pod
 ↓
nginx
```

If that Pod is deleted, you have not declared that another identical Pod should necessarily be created.

You declared:

> "I want this Pod."

For an application, you usually want something stronger:

> "I want this application to continuously have N instances."

That is where workload controllers such as ReplicaSets and Deployments become important.

---

# 7. ReplicaSet

A **ReplicaSet** maintains a specified number of matching Pods.

For example:

```yaml
spec:
  replicas: 3
```

means the desired number is:

```text
3 Pods
```

Conceptually:

```text
              ReplicaSet
                   │
        ┌──────────┼──────────┐
        ↓          ↓          ↓
      Pod 1      Pod 2      Pod 3
```

If one disappears:

```text
Desired = 3
Actual  = 2
```

The ReplicaSet works to restore:

```text
Desired = 3
Actual  = 3
```

ReplicaSets use label selectors to identify the Pods they manage.

---

# 8. Deployment

A **Deployment** is a higher-level workload object used primarily for managing stateless applications.

The fundamental relationship is:

```text
Deployment
     ↓
ReplicaSet
     ↓
Pods
     ↓
Containers
```

For example:

```text
                 Deployment
                     │
                     ↓
                 ReplicaSet
                     │
          ┌──────────┼──────────┐
          ↓          ↓          ↓
        Pod 1      Pod 2      Pod 3
```

---

## Why Use a Deployment?

ReplicaSets maintain Pod replicas.

Applications also need lifecycle and release management.

Deployments provide mechanisms for:

- Declarative application updates
- Scaling
- Rolling updates
- Rollbacks
- Revision history
- Managing ReplicaSets

For a typical stateless application, you normally create a Deployment rather than manually managing individual Pods.

---

# 9. Deployment Manifest

```yaml
apiVersion: apps/v1
kind: Deployment

metadata:
  name: nginx

spec:
  replicas: 3

  selector:
    matchLabels:
      app: nginx

  template:
    metadata:
      labels:
        app: nginx

    spec:
      containers:
        - name: nginx
          image: nginx:1.27
```

The structure is:

```text
Deployment
│
├── replicas
│
├── selector
│
└── template
       │
       └── Pod definition
```

The `template` describes the Pods the Deployment wants to create.

---

# 10. Deployment Template

This section:

```yaml
template:
  metadata:
    labels:
      app: nginx

  spec:
    containers:
      - name: nginx
        image: nginx:1.27
```

is a Pod template.

It tells the Deployment:

> "Create Pods according to this template."

The resulting relationship is:

```text
Deployment
    ↓
ReplicaSet
    ↓
Pods
```

---

# 11. Labels and Selectors

The Deployment contains:

```yaml
selector:
  matchLabels:
    app: nginx
```

The Pod template contains:

```yaml
labels:
  app: nginx
```

These must correspond correctly.

Conceptually:

```text
Deployment
    │
    │ selector: app=nginx
    ↓
ReplicaSet
    │
    │ manages matching Pods
    ↓
Pods
    │
    ├── app=nginx
    ├── app=nginx
    └── app=nginx
```

Labels and selectors are fundamental to Kubernetes object relationships.

# 13. Scaling a Deployment

Suppose the Deployment has:

```yaml
replicas: 3
```

Scale it to five:

```bash
kubectl scale deployment nginx --replicas=5
```

Kubernetes works toward:

```text
Deployment
    ↓
ReplicaSet
    ↓
Pod Pod Pod Pod Pod
```

You can also declare the desired state directly in YAML:

```yaml
spec:
  replicas: 5
```

---

# 14. Rolling Updates

Suppose the current image is:

```text
nginx:1.27
```

and you want:

```text
nginx:1.28
```

Update:

```yaml
containers:
  - name: nginx
    image: nginx:1.28
```

Then:

```bash
kubectl apply -f deployment.yaml
```

The Deployment can perform a rolling update, progressively replacing Pods associated with the previous revision with Pods from the new revision.

Conceptually:

```text
Old ReplicaSet
    ↓
v1.27 Pods

       ↓ update

New ReplicaSet
    ↓
v1.28 Pods
```

The exact rollout behavior is controlled by Deployment strategy settings.

---

# 16. Rollbacks

If a new version has a problem, you can roll back:

```bash
kubectl rollout undo deployment nginx
```

Check:

```bash
kubectl rollout status deployment nginx
```

A Deployment can return to an earlier revision when that revision is available in its rollout history.

# 18. Pod vs ReplicaSet vs Deployment

| Object | Main Purpose |
|---|---|
| Pod | Runs one or more tightly coupled containers |
| ReplicaSet | Maintains the desired number of matching Pods |
| Deployment | Manages application releases and ReplicaSets |

The relationship is:

```text
Deployment
     ↓
ReplicaSet
     ↓
Pods
     ↓
Containers
```

For a normal stateless application:

> **Deployment is usually the object you interact with; Kubernetes manages the lower-level ReplicaSet and Pods.**

---

# 19. End-to-End Example

Consider:

```yaml
apiVersion: apps/v1
kind: Deployment

metadata:
  name: web

spec:
  replicas: 3

  selector:
    matchLabels:
      app: web

  template:
    metadata:
      labels:
        app: web

    spec:
      containers:
        - name: nginx
          image: nginx:1.27
```

The intended result is:

```text
                    Deployment
                       web
                        │
                        ↓
                    ReplicaSet
                        │
            ┌───────────┼───────────┐
            ↓           ↓           ↓
          Pod 1       Pod 2       Pod 3
            │           │           │
          nginx       nginx       nginx
```

Desired state:

```text
3 Pods running nginx:1.27
```

If one Pod disappears:

```text
Desired = 3
Actual  = 2
```

The controller hierarchy works to restore:

```text
Desired = 3
Actual  = 3
```
