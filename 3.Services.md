# Kubernetes Services 

# 1. Introduction to Kubernetes Services

A **Kubernetes Service** provides a stable network endpoint through which applications can communicate with a set of Pods.

Pods are temporary and can be:

- Created
- Deleted
- Restarted
- Rescheduled
- Replaced during deployments
- Assigned different IP addresses

Because Pod IP addresses are not stable, applications should generally not communicate directly with individual Pod IPs.

A Service solves this problem by providing a stable abstraction in front of one or more Pods.

### Basic idea

```text
Client
   |
   v
Service
   |
   +----------+----------+
   |          |          |
   v          v          v
 Pod 1      Pod 2      Pod 3
```

The client communicates with the Service rather than depending on individual Pod IP addresses.

---

# 2. Why Do We Need Services?

Consider a Deployment with three application Pods:

```text
frontend
   |
   v
backend Pods

Pod 1 -> 10.244.1.10
Pod 2 -> 10.244.2.15
Pod 3 -> 10.244.1.21
```

The frontend needs to communicate with the backend.

If the frontend directly uses:

```text
10.244.1.10
```

there is a problem.

If Pod 1 is deleted, Kubernetes may create a replacement:

```text
10.244.3.8
```

The frontend's old destination is no longer valid.

A Service provides a stable endpoint:

```text
frontend
   |
   v
backend-service
10.96.10.20
   |
   +--------+--------+
   |        |        |
   v        v        v
 Pod 1    Pod 2    Pod 3
```

The Pods can change while the Service remains stable.

---

# 3. The Problem with Pod IP Addresses

Pod IP addresses are generally **ephemeral**.

For example:

```text
Before:
Pod A -> 10.244.1.10
Pod B -> 10.244.1.11

After Pod A is recreated:
Pod A -> 10.244.3.25
Pod B -> 10.244.1.11
```

Applications should not normally hard-code these addresses.

Kubernetes Services provide:

1. A stable virtual IP
2. A stable DNS name
3. A mechanism for selecting backend Pods
4. Load distribution across eligible backend endpoints
5. A consistent abstraction for internal or external connectivity

---

# 4. What Is a Kubernetes Service?

A Service is a Kubernetes API object that defines a logical set of endpoints and provides a stable way to access them.

A typical Service has:

- A name
- A virtual IP
- One or more ports
- A selector
- A Service type
- Backend endpoints

Example:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: backend-service
spec:
  selector:
    app: backend
  ports:
    - port: 80
      targetPort: 8080
  type: ClusterIP
```

This means:

> Create a Service named `backend-service`, find Pods with the label `app: backend`, and forward Service port 80 to port 8080 on those Pods.

---

# 5. How a Service Works

The process can be simplified as:

```text
Application
     |
     | request
     v
Service DNS
     |
     v
Service Virtual IP
     |
     v
Service routing
     |
     v
Selected backend endpoint
     |
     v
Pod
```

For example:

```text
http://backend-service:80
```

may ultimately send traffic to:

```text
10.244.2.15:8080
```

The application does not need to know the Pod IP.

---

# 6. Service and Pod Relationship

A Service usually identifies its backend Pods using a **label selector**.

Example Pods:

```yaml
metadata:
  labels:
    app: backend
```

Service:

```yaml
spec:
  selector:
    app: backend
```

Therefore:

```text
Service
   |
   | selector: app=backend
   |
   +------ Pod 1: app=backend
   +------ Pod 2: app=backend
   +------ Pod 3: app=backend
```

If another Pod has:

```yaml
labels:
  app: frontend
```

it will not be selected.

---

# 7. Labels and Selectors

Labels are key-value metadata attached to Kubernetes objects.

Example:

```yaml
labels:
  app: web
  environment: production
```

A Service can select Pods using:

```yaml
selector:
  app: web
```

This is one of the most important concepts in Kubernetes networking.

### Example

Pods:

| Pod | Label |
|---|---|
| pod-1 | app=web |
| pod-2 | app=web |
| pod-3 | app=api |

Service:

```yaml
selector:
  app: web
```

Selected endpoints:

```text
pod-1
pod-2
```

`pod-3` is not selected.

### Important

A Service does **not** select Pods based on their names.

It normally selects them using labels.

---

# 8. Service Types

Kubernetes provides several Service types.

The major types are:

```text
ClusterIP
NodePort
LoadBalancer
ExternalName
```

There is also an important special configuration:

```text
Headless Service
```

which is created by setting:

```yaml
clusterIP: None
```

### High-level comparison

| Type | Main purpose |
|---|---|
| ClusterIP | Internal cluster access |
| NodePort | Expose service through a port on each node |
| LoadBalancer | Expose service using an external load balancer |
| ExternalName | Map a Service name to an external DNS name |
| Headless | Direct service discovery of individual Pods |

---

# 9.1 ClusterIP

`ClusterIP` is the default Service type.

It exposes the Service internally inside the Kubernetes cluster.

Example:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: backend
spec:
  type: ClusterIP
  selector:
    app: backend
  ports:
    - port: 80
      targetPort: 8080
```

Applications inside the cluster can access:

```text
backend:80
```

or:

```text
backend.default.svc.cluster.local
```

assuming the Service is in the `default` namespace.

### Traffic flow

```text
Frontend Pod
     |
     v
backend:80
     |
     v
ClusterIP
     |
     v
Backend Pod:8080
```

### Typical use cases

- Backend APIs
- Internal databases
- Internal microservices
- Internal application communication

---

# 9.2 NodePort

`NodePort` exposes a Service through a port on each Kubernetes node.

Example:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: web-service
spec:
  type: NodePort
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 8080
      nodePort: 30080
```

The application can be accessed through:

```text
<NodeIP>:30080
```

Traffic flow:

```text
External Client
      |
      v
Node IP:30080
      |
      v
NodePort Service
      |
      v
Pod:8080
```

### NodePort range

Kubernetes commonly uses:

```text
30000-32767
```

as the default NodePort range.

The exact range can be changed through Kubernetes API server configuration.

### Advantages

- Simple external access
- Useful for learning and testing
- Works without an external load balancer

### Disadvantages

- Exposes a high-numbered port
- Less convenient for production applications
- Does not by itself provide the features normally expected from a cloud load balancer
- Usually not the preferred way to expose HTTP/HTTPS applications in production

---

# 9.3 LoadBalancer

`LoadBalancer` is commonly used to expose a Service externally through an infrastructure/cloud load balancer.

Example:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: web-service
spec:
  type: LoadBalancer
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 8080
```

In a cloud environment, Kubernetes can request an external load balancer from the cloud provider integration.

Traffic generally looks like:

```text
Internet
   |
   v
Cloud Load Balancer
   |
   v
Kubernetes Service
   |
   v
Pods
```

### Common use cases

- Public web applications
- Public APIs
- External-facing services

### Important

The exact behavior and capabilities depend on the Kubernetes environment and its cloud/load-balancer integration.

---

# 9.4 ExternalName

`ExternalName` allows a Service name to refer to an external DNS name.

Example:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: external-db
spec:
  type: ExternalName
  externalName: database.example.com
```

Applications can use:

```text
external-db
```

instead of directly using:

```text
database.example.com
```

Conceptually:

```text
Application
    |
    v
external-db
    |
    v
database.example.com
```

An `ExternalName` Service is different from a normal Service backed by Pod endpoints.

---

# 9.5 Headless Services

A Headless Service does not allocate a normal ClusterIP.

It is created using:

```yaml
clusterIP: None
```

Example:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: database
spec:
  clusterIP: None
  selector:
    app: database
  ports:
    - port: 5432
      targetPort: 5432
```

Instead of giving clients a single virtual IP, DNS can return the addresses of the individual selected Pods.

### Why use a Headless Service?

Common use cases include:

- Stateful applications
- Databases
- Distributed systems
- Applications that need to discover individual instances

### Conceptual difference

Normal Service:

```text
client
  |
  v
Service IP
  |
  +---- Pod
  +---- Pod
  +---- Pod
```

Headless Service:

```text
client
  |
  v
DNS
  |
  +---- Pod IP 1
  +---- Pod IP 2
  +---- Pod IP 3
```

# 10. Service Discovery

Service discovery allows applications to find other services without knowing their IP addresses.

For example:

```text
frontend
   |
   | requests backend
   v
backend-service
```

The frontend does not need to know:

```text
10.244.1.12
10.244.2.14
10.244.3.18
```

It can simply use:

```text
backend-service
```

Kubernetes provides DNS-based service discovery through the cluster DNS system.

---

# 11. DNS-Based Service Discovery

Suppose:

```text
Service = backend
Namespace = production
```

The fully qualified DNS name is generally:

```text
backend.production.svc.cluster.local
```

The components are:

```text
backend
   |
   +-- Service name

production
   |
   +-- Namespace

svc
   |
   +-- Kubernetes Service DNS domain

cluster.local
   |
   +-- Cluster DNS domain
```

Within the same namespace, applications can usually use:

```text
backend
```

They can also use:

```text
backend.production
```

or the fully qualified name:

```text
backend.production.svc.cluster.local
```

# 12. Kubernetes Service Networking

A Service provides a stable virtual endpoint.

For a typical ClusterIP Service:

```text
Service:
Name       = backend
ClusterIP  = 10.96.20.10
Port       = 80

Backend:
Pod 1 = 10.244.1.10:8080
Pod 2 = 10.244.2.20:8080
Pod 3 = 10.244.3.30:8080
```

Traffic:

```text
Client
  |
  | backend:80
  v
ClusterIP 10.96.20.10:80
  |
  +-------------------+
  |                   |
  v                   v
Pod 1:8080        Pod 2:8080
```

The Service abstraction hides the changing Pod IPs.

---

# 13. kube-proxy

`kube-proxy` is a Kubernetes component involved in implementing Service networking on nodes.

Depending on the Kubernetes networking implementation and configuration, it can program packet-processing rules using mechanisms such as:

- iptables
- IPVS
- nftables in supported configurations

Its job includes helping implement the forwarding behavior associated with Services.

Conceptually:

```text
Service IP
    |
    v
Node networking rules
    |
    v
Backend endpoint
```

### Important distinction

`kube-proxy` is not the same thing as:

- CoreDNS
- Ingress Controller
- CNI plugin

They solve different networking problems.

---

# 14. Endpoints and EndpointSlices

A Service needs to know which backend endpoints are available.

Kubernetes represents Service backends using endpoint-related API objects.

Modern Kubernetes uses **EndpointSlices** as the scalable representation of Service endpoints.

Conceptually:

```text
Service
   |
   v
EndpointSlice
   |
   +--- Pod IP 1
   +--- Pod IP 2
   +--- Pod IP 3
```

You can inspect EndpointSlices with:

```bash
kubectl get endpointslices
```

You can also inspect a particular Service's endpoints through:

```bash
kubectl describe service <service-name>
```

### Why EndpointSlices?

EndpointSlices improve scalability compared with putting a very large number of endpoints into one traditional Endpoints object.

# 15. Service YAML

A basic Service definition:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: web-service
  namespace: default
spec:
  type: ClusterIP
  selector:
    app: web
  ports:
    - protocol: TCP
      port: 80
      targetPort: 8080
```

### Important fields

#### apiVersion

```yaml
apiVersion: v1
```

The API version for the Service object.

#### kind

```yaml
kind: Service
```

Specifies that the resource is a Service.

#### metadata.name

```yaml
name: web-service
```

The Service name.

#### selector

```yaml
selector:
  app: web
```

Selects Pods with:

```text
app=web
```

#### ports

Defines the ports exposed by the Service.

# 18. Port, TargetPort, and NodePort

This is one of the most important Service concepts.

Consider:

```yaml
ports:
  - port: 80
    targetPort: 8080
    nodePort: 30080
```

There are three different ports.

## 18.1 port

The port exposed by the Service.

```yaml
port: 80
```

Clients connect to:

```text
Service:80
```

## 18.2 targetPort

The port on the backend Pod.

```yaml
targetPort: 8080
```

Traffic is forwarded to:

```text
Pod:8080
```

## 18.3 nodePort

The port exposed on each node for a NodePort Service.

```yaml
nodePort: 30080
```

External clients can use:

```text
NodeIP:30080
```

### Traffic flow

```text
Client
   |
   | NodeIP:30080
   v
NodePort
   |
   | Service port 80
   v
Service
   |
   | targetPort 8080
   v
Pod:8080
```

### Quick memory trick

```text
nodePort -> Node
port     -> Service
targetPort -> Pod
```

---

# 19. Multiple Ports

A Service can expose multiple ports.

Example:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: application
spec:
  selector:
    app: application
  ports:
    - name: http
      protocol: TCP
      port: 80
      targetPort: 8080

    - name: metrics
      protocol: TCP
      port: 9090
      targetPort: 9090
```

The Service exposes:

```text
Service:80
Service:9090
```

The Pods receive:

```text
Pod:8080
Pod:9090
```

When defining multiple Service ports, each port should have a unique name.

---

# 20. Service Without a Selector

A Service can exist without a selector.

Example:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: external-service
spec:
  ports:
    - port: 80
```

This is useful when the backend is not represented by normal Kubernetes Pods selected by labels.

A common pattern is to manually define corresponding endpoint information using the appropriate Kubernetes endpoint mechanisms.

Conceptually:

```text
Service
   |
   v
External endpoint
```

This can be useful when integrating Kubernetes applications with external systems.

---

# 21. External Traffic Policy

For Services that receive traffic from outside the cluster, Kubernetes provides the `externalTrafficPolicy` field.

Two common values are:

```yaml
externalTrafficPolicy: Cluster
```

and:

```yaml
externalTrafficPolicy: Local
```

## Cluster

Traffic can be routed to an eligible backend endpoint on another node.

Conceptually:

```text
Client
  |
  v
Node A
  |
  v
Node B
  |
  v
Pod
```

## Local

Traffic is preferentially handled by endpoints local to the receiving node.

Conceptually:

```text
Client
  |
  v
Node A
  |
  v
Pod on Node A
```

`Local` can be useful in scenarios where preserving the original client source IP is important.

However, it can also create uneven traffic distribution if endpoints are not spread appropriately across nodes.

# 22. Session Affinity

By default, a Service can distribute connections among its available endpoints.

You can configure session affinity:

```yaml
sessionAffinity: ClientIP
```

This can cause requests from the same client IP to be directed to the same backend endpoint for the configured affinity period.

Default:

```yaml
sessionAffinity: None
```

Example:

```yaml
spec:
  sessionAffinity: ClientIP
```

### When might it be useful?

Some legacy applications maintain session state locally.

However, for cloud-native applications, it is generally preferable to make applications stateless where possible.

---

# 23. Service Traffic and Load Balancing

A Service can distribute traffic across its available backend endpoints.

Example:

```text
Service
   |
   +---- Pod A
   |
   +---- Pod B
   |
   +---- Pod C
```

Requests can be forwarded to different endpoints.

The exact traffic behavior depends on:

- Kubernetes version
- kube-proxy implementation
- CNI/networking implementation
- Service configuration
- Endpoint readiness

### Important

A Service is not the same as an application-level load balancer such as an HTTP reverse proxy.

A Service primarily provides Kubernetes networking and stable endpoint abstraction.

# 25. Service with Ingress

Ingress and Service are different resources.

A typical web architecture looks like:

```text
Internet
   |
   v
Ingress / Ingress Controller
   |
   +------------------+
   |                  |
   v                  v
frontend-service   api-service
   |                  |
   v                  v
frontend Pods       API Pods
```

Ingress commonly handles HTTP/HTTPS routing.

For example:

```text
example.com/
       |
       v
frontend-service

example.com/api
       |
       v
api-service
```

The Service provides stable access to the backend Pods.

The Ingress provides HTTP/HTTPS routing rules.

# 26. Service with Deployment

A very common Kubernetes architecture is:

```text
Deployment
    |
    +---- Pod
    +---- Pod
    +---- Pod
          ^
          |
       Service
```

Example:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: nginx
          ports:
            - containerPort: 80
```

Service:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: web-service
spec:
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 80
```

The key connection is:

```text
Deployment Pod label
        |
        | app=web
        v
Service selector
        |
        v
Backend endpoints
```

# 29. Scaling and Services

Suppose:

```text
Deployment replicas = 3
```

The Service may have:

```text
Pod 1
Pod 2
Pod 3
```

Scale the Deployment:

```bash
kubectl scale deployment nginx-deployment --replicas=5
```

Now the Service can discover the newly eligible Pods automatically through the Kubernetes endpoint machinery.

The application does not need to be manually reconfigured with the new Pod IP addresses.

# 30. Service During Rolling Updates

Suppose the Deployment initially has:

```text
Pod A
Pod B
Pod C
```

A new application version is deployed.

Kubernetes gradually replaces old Pods with new Pods.

The Service continues providing the stable endpoint while the set of eligible backend endpoints changes.

Conceptually:

```text
              Service
                 |
       +---------+---------+
       |         |         |
       v         v         v
    New Pod   New Pod   Old Pod
```

Later:

```text
              Service
                 |
       +---------+---------+
       |         |         |
       v         v         v
    New Pod   New Pod   New Pod
```

This is one of the reasons Services are essential to Kubernetes application deployments.

# 31. Readiness and Service Traffic

A Pod can be running but not ready to receive traffic.

Example:

```text
Pod status:
Running = Yes
Ready   = No
```

Kubernetes can use readiness information when determining whether a Pod should receive Service traffic.

This is extremely important for:

- Application startup
- Rolling deployments
- Slow initialization
- Dependency checks
- Zero-downtime deployment strategies

A typical application should expose a readiness probe.

Example:

```yaml
readinessProbe:
  httpGet:
    path: /health
    port: 8080
  initialDelaySeconds: 5
  periodSeconds: 10
```

# 33. Troubleshooting Services

When a Service does not work, follow a systematic process.

## Step 1 — Check the Service

```bash
kubectl get svc
```

Verify:

- Service exists
- Correct type
- Correct port
- Correct ClusterIP

---

## Step 2 — Describe the Service

```bash
kubectl describe svc <service-name>
```

Check:

```text
Selector
Endpoints
Port
TargetPort
```

---

## Step 3 — Check the Pods

```bash
kubectl get pods
```

Then:

```bash
kubectl get pods -o wide
```

Check:

- Pod status
- Pod IP
- Ready status
- Node

---

## Step 4 — Check Labels

```bash
kubectl get pods --show-labels
```

Compare the labels with the Service selector.

For example:

Service:

```yaml
selector:
  app: backend
```

Pods must have:

```yaml
labels:
  app: backend
```

---

## Step 5 — Check EndpointSlices

```bash
kubectl get endpointslices
```

If the Service has no usable endpoints, investigate:

- Selector mismatch
- Pods not ready
- Wrong namespace
- Incorrect labels
- Failed application health checks


Then:

```bash
curl http://<service-name>:<port>
```

# 34. Common Service Problems

## Problem 1 — Service has no endpoints

Example:

```text
Endpoints: <none>
```

Likely causes:

- Incorrect selector
- Pod labels do not match
- Pods are not Ready
- Service and Pods are in different namespaces

---

## Problem 2 — Wrong targetPort

Service:

```yaml
port: 80
targetPort: 8080
```

But application listens on:

```text
8081
```

Result:

```text
Connection failure
```

The `targetPort` must correspond to the port where the application is actually listening.

---

## Problem 3 — Wrong Service selector

Pods:

```yaml
labels:
  app: frontend
```

Service:

```yaml
selector:
  app: backend
```

Result:

```text
No matching backend Pods
```

---

## Problem 4 — Application listens only on localhost

Suppose an application listens on:

```text
127.0.0.1:8080
```

rather than:

```text
0.0.0.0:8080
```

Other Pods may not be able to reach it through the Service.

Applications intended to receive network traffic from outside their own process/container generally need to listen on an appropriate non-loopback interface.

---

# 35. Common Mistakes

### Mistake 1 — Confusing port and targetPort

Remember:

```text
port       = Service port
targetPort = Pod/application port
```

### Mistake 2 — Forgetting labels

The Service selector must match the Pod labels.

### Mistake 3 — Testing a ClusterIP from the public Internet

A ClusterIP is intended for cluster-internal access.

### Mistake 4 — Assuming Service IP is a Pod IP

They are different concepts.

```text
Service IP != Pod IP
```

### Mistake 5 — Assuming NodePort means "production load balancer"

NodePort provides node-level port exposure. Production architectures often use LoadBalancer and/or Ingress depending on requirements.

### Mistake 6 — Ignoring readiness

A Running Pod is not necessarily ready to receive application traffic.

# 36. Best Practices

## 36.1 Use meaningful Service names

Prefer:

```text
user-service
payment-service
order-service
```

over:

```text
service1
service2
test-service
```

---

## 36.2 Use consistent labels

Example:

```yaml
labels:
  app: payment
  component: backend
```

Then:

```yaml
selector:
  app: payment
```

---

## 36.3 Keep application ports clear

Document the relationship:

```text
Service port  -> 80
Pod port      -> 8080
```

---

## 36.4 Use readiness probes

Readiness probes help prevent traffic from reaching applications that are not ready.

---

## 36.5 Prefer stateless applications when possible

Avoid relying unnecessarily on sticky sessions.

If sessions are required, consider external session storage such as a database or distributed cache.

---

## 36.6 Use Ingress for HTTP/HTTPS routing when appropriate

Instead of creating a separate external LoadBalancer for every HTTP application, an Ingress architecture can provide centralized HTTP/HTTPS routing.

Example:

```text
                    Internet
                       |
                       v
                Ingress Controller
                  /           \
                 /             \
                v               v
        frontend-service    api-service
             |                   |
             v                   v
        frontend Pods        API Pods
```

# 37. Service vs Ingress

| Feature | Service | Ingress |
|---|---|---|
| Purpose | Stable network access to Pods | HTTP/HTTPS routing |
| Layer | Primarily network/service abstraction | Application-layer HTTP/HTTPS routing |
| Pod discovery | Yes | Usually through Services |
| Stable endpoint | Yes | Typically via Ingress entry point |
| Path routing | Not normally | Yes |
| Host-based routing | Not normally | Yes |
| TLS termination | Not the core Service function | Commonly supported by Ingress controllers |
| Load balancing | Service-level traffic distribution | HTTP/HTTPS routing/load balancing through controller |

### Example

Service:

```text
api-service
```

Ingress:

```text
/api -> api-service
```

---

# 38. Service vs Pod

| Feature | Pod | Service |
|---|---|---|
| Runs application container(s) | Yes | No |
| Has IP | Yes | Has virtual Service IP depending on type/configuration |
| IP stability | Not guaranteed | Designed to provide stable access |
| Lifecycle | Temporary/replaceable | Stable API object |
| Scaling | Managed by controllers such as Deployment | Selects available endpoints |
| DNS name | Pod DNS can exist | Stable Service DNS |
| Main purpose | Run workload | Provide network access to workloads |

# 40. End-to-End Architecture

A common Kubernetes web application architecture:

```text
                         Internet
                            |
                            v
                    +---------------+
                    | Load Balancer |
                    +---------------+
                            |
                            v
                    +---------------+
                    |    Ingress    |
                    +---------------+
                       /         \
                      /           \
                     v             v
             frontend-service   api-service
                    |               |
                    v               v
              +-----+-----+   +-----+-----+
              |           |   |           |
              v           v   v           v
           Frontend     Frontend       API Pods
             Pod          Pod

                              |
                              v
                       database-service
                              |
                              v
                       Database Pods
```

This architecture separates responsibilities:

- Load balancer provides external connectivity.
- Ingress handles HTTP/HTTPS routing.
- Services provide stable access to workloads.
- Deployments manage stateless application Pods.
- Stateful workloads can use StatefulSets and appropriate Services.

# 41. Important Interview Questions

## Q1. What is a Kubernetes Service?

A Service provides a stable network endpoint for accessing a logical group of Pods.

---

## Q2. Why do we need Services?

Because Pod IP addresses are ephemeral and can change when Pods are recreated.

---

## Q3. What is the default Service type?

```text
ClusterIP
```

---

## Q4. What is ClusterIP?

ClusterIP provides internal cluster access to a Service.

---

## Q5. What is NodePort?

NodePort exposes a Service through a port on each node.

---

## Q6. What is LoadBalancer?

LoadBalancer can provision or integrate with an external load-balancing mechanism, especially in cloud environments.

---

## Q7. What is a Headless Service?

A Service configured with:

```yaml
clusterIP: None
```

It does not provide a normal virtual ClusterIP and is useful for direct endpoint discovery.

---

## Q8. What is the difference between `port` and `targetPort`?

```text
port       = Service port
targetPort = backend Pod port
```

---

## Q9. What is NodePort?

It is the port exposed on the Kubernetes nodes for a NodePort Service.

---

## Q10. How does a Service find Pods?

Typically using a label selector.

---

## Q11. What happens if the Service selector does not match any Pods?

The Service has no matching backend endpoints.

---

## Q12. What is Service Discovery?

It is the mechanism that allows applications to locate Services without manually knowing their IP addresses.

---

## Q13. How does Kubernetes provide DNS-based Service discovery?

The cluster DNS service creates DNS records for Services.

---

## Q14. What is the DNS name of a Service?

A typical fully qualified Service DNS name is:

```text
<service>.<namespace>.svc.cluster.local
```

---

## Q15. What is kube-proxy?

It is a node-level Kubernetes component involved in implementing Service networking and forwarding behavior.

---

## Q16. What is the difference between Service and Ingress?

A Service provides stable access to backend endpoints, while Ingress is commonly used for HTTP/HTTPS routing into Services.

---

## Q17. Can a Service exist without a selector?

Yes.

This can be useful when manually associating a Service with endpoints outside the normal Pod selector model.

---

## Q18. What is EndpointSlice?

EndpointSlice is a scalable Kubernetes API representation of network endpoints associated with Services.
